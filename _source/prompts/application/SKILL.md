# 阶段 4：应用层设计（Application Layer Design）

基于前置阶段的文档，通过对话设计应用层的用例、业务规则、流程编排，并生成文件骨架。

## 前置依赖

**必须读取**：
- `.cdd/01-requirements.md`（需求文档）
- `.cdd/02-architecture.md`（架构设计文档）
- `.cdd/03-data-layer.md`（数据层设计文档）

如果这些文件不存在，提示用户先完成前置阶段。

## 核心概念

参见 [GLOSSARY.md](../GLOSSARY.md) 中的术语定义：
- **@intent**：描述文件功能（必须标注）
- **@dependency**：通过 import 语句自动提取（不需要手动标注）
- **@contract**、**@step**、**@boundary**：函数契约标注

## 工作流程

### 1. 识别用例（Use Cases）

从需求文档中识别核心用例：
- 每个用户操作对应一个用例
- 每个用例封装一个完整的业务流程

**询问用户确认**：
- "根据需求文档，我识别出以下用例：[用例1]、[用例2]、[用例3]，是否正确？"
- "是否还有其他用例需要添加？"

### 2. 设计业务规则

针对每个用例，设计业务规则和验证逻辑：

**询问或推荐**：
- 这个用例有哪些业务规则？
- 需要验证哪些前置条件？
- 成功和失败的标准是什么？
- 是否需要事务处理？

**业务规则设计原则**：
- **框架无关**：业务规则不依赖具体的框架或技术
- **可测试**：业务规则应该易于单元测试
- **明确性**：规则应该清晰明确，避免歧义
- **一致性**：相同的规则在不同场景下保持一致

### 3. 设计应用服务

针对每个用例，设计应用服务（Application Service）：

**应用服务设计原则**：
- **编排职责**：协调数据层的多个操作
- **无状态**：服务不应该持有状态
- **单一用例**：每个服务方法对应一个用例
- **错误处理**：服务应该处理所有可能的错误情况

**常见服务类型**：
- 命令服务（Command Service）：处理写操作
- 查询服务（Query Service）：处理读操作
- 工作流服务（Workflow Service）：处理复杂的多步骤流程

### 4. 设计上下文管理

针对需要共享状态的场景，设计上下文管理器（Context Manager）：

**上下文管理器的作用**：
- 管理会话状态（例如：当前用户、当前会话）
- 管理应用配置（例如：运行时配置）
- 管理临时数据（例如：缓存、草稿）

**上下文设计原则**：
- **生命周期明确**：明确上下文的创建和销毁时机
- **作用域明确**：明确上下文的作用范围（全局/会话级/请求级）
- **避免滥用**：不要把所有状态都放到上下文中

### 5. 设计依赖关系

确定应用层对数据层的依赖：

**依赖设计原则**：
- **依赖倒置**：应用层依赖数据层的接口，而非具体实现
- **单向依赖**：应用层 → 数据层，严格单向
- **最小依赖**：只依赖必要的数据层模块

### 6. 生成文件骨架

根据设计生成文件骨架（@intent + import + 函数签名）：

**生成内容**：
1. **用例/命令处理器**（`src/application/commands/`）
2. **应用服务**（`src/application/services/`）
3. **上下文管理器**（`src/application/context/`）

**文件骨架包含**：
- `@intent` 注释：描述文件的功能
- `import` 语句：声明依赖的数据层模块和其他应用层模块
- `@contract`、`@step`、`@boundary`：函数契约
- 函数签名：只有签名，不实现具体逻辑（抛出 `throw new Error('Not implemented')`）

## 对话原则

1. **基于需求设计**：所有用例都应该来自需求文档
2. **避免过度设计**：不要设计用不到的用例和服务
3. **考虑可测试性**：设计应该便于单元测试
4. **保持简单**：优先使用简单的流程编排，避免复杂的状态机
5. **验证理解**：定期总结已设计的用例和服务，确保理解一致

## 输出格式

当所有应用层设计完成后，输出设计文档和文件骨架。

设计文档结构参见 [OUTPUT-FORMAT.md](OUTPUT-FORMAT.md)。

## 特殊情况处理

### 当用例过多时
建议按业务领域分组，每个领域一个子目录。

### 当依赖复杂时
使用依赖注入模式，将依赖作为参数传入。

### 当业务规则复杂时
考虑使用规则引擎或策略模式。

### 当循环依赖出现时
重新设计模块边界，提取共享逻辑到独立模块。

## 注意事项

- **必须标注 @intent**：每个文件都必须在顶部标注 @intent
- **依赖通过 import 声明**：不需要手动标注 @dependency，系统会自动从 import 语句中提取
- **应用层不依赖适配层**：依赖方向是 适配层 → 应用层 → 数据层
- **避免在应用层写 UI 逻辑**：UI 逻辑应该在适配层
- **保持用例简单**：复杂的数据操作应该在数据层的 Service 中
- **使用 @contract、@step、@boundary**：为所有函数标注契约

## 最终交付物

当所有应用层设计完成后：

1. 将设计文档保存为 `.cdd/04-application-layer.md`
2. 生成应用层文件骨架到 `src/application/` 目录：
   - `src/application/commands/` - 命令处理器骨架
   - `src/application/services/` - 应用服务骨架
   - `src/application/context/` - 上下文管理器骨架
3. **每个文件都必须标注 @intent**
4. **每个函数都必须标注 @contract、@step、@boundary**
5. **依赖关系通过 import 语句声明**

该文档和代码将作为下一阶段（适配层设计）的输入。

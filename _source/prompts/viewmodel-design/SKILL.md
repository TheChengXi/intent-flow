# 阶段 4：ViewModel 层设计

基于前置阶段的文档，通过对话设计 ViewModel 层的状态管理、命令处理、上下文管理，并生成文件骨架。

## 前置依赖

**必须读取**：
- `.cdd/01-requirements.md`（需求文档）
- `.cdd/02-architecture.md`（架构设计文档）
- `.cdd/03-model-design.md`（Model 层设计文档）

如果这些文件不存在，提示用户先完成前置阶段。

## 核心概念

参见 [GLOSSARY.md](../GLOSSARY.md) 中的术语定义：
- **@intent**：描述文件功能（必须标注）
- **@dependency**：通过 import 语句自动提取（不需要手动标注）
- **@contract**、**@step**、**@boundary**：函数契约标注

## 工作流程

### 1. 识别功能模块

从需求文档中识别需要哪些功能模块：
- 每个核心功能对应一个 ViewModel
- 每个 ViewModel 负责一类用户操作

**询问用户确认**：
- "根据需求文档，我识别出以下功能模块：[模块1]、[模块2]、[模块3]，是否正确？"
- "是否还有其他功能模块需要添加？"

### 2. 设计状态管理

针对每个功能模块，设计需要管理的状态：

**询问或推荐**：
- 这个模块需要管理哪些状态？
- 状态的初始值是什么？
- 状态如何更新？
- 状态是否需要持久化？

**状态设计原则**：
- **最小化原则**：只管理必要的状态
- **单一数据源**：避免状态冗余
- **不可变性**：状态更新应该是不可变的
- **可序列化**：状态应该可以序列化

### 3. 设计命令处理

针对每个用户操作，设计命令处理器（Command）：

**命令设计原则**：
- **单一职责**：每个命令只处理一个用户操作
- **无状态**：命令不应该持有状态
- **可测试**：命令应该易于单元测试
- **错误处理**：命令应该处理所有可能的错误情况

**常见命令类型**：
- 创建命令、更新命令、删除命令、查询命令、业务命令

### 4. 设计上下文管理

针对需要共享状态的场景，设计上下文管理器（Context Manager）：

**上下文管理器的作用**：
- 管理会话状态（例如：当前用户、当前项目）
- 管理全局配置（例如：主题、语言）
- 管理临时数据（例如：表单草稿、选中项）

**上下文设计原则**：
- **生命周期明确**：明确上下文的创建和销毁时机
- **作用域明确**：明确上下文的作用范围（全局/模块级/组件级）
- **避免滥用**：不要把所有状态都放到上下文中

### 5. 设计角色/功能模块

将相关的命令、状态、上下文组织成角色（Role）或功能模块：

**角色设计原则**：
- **高内聚**：相关的功能放在一起
- **低耦合**：角色之间松散耦合
- **单一职责**：每个角色只负责一类功能

### 6. 生成文件骨架

根据设计生成文件骨架（@intent + import + 函数签名）：

**生成内容**：
1. **命令处理器**（`src/viewmodel/commands/`）
2. **上下文管理器**（`src/viewmodel/context/`）
3. **角色/功能模块**（`src/viewmodel/roles/`）

**文件骨架包含**：
- `@intent` 注释：描述文件的功能
- `import` 语句：声明依赖的 Model 层模块和其他 ViewModel 模块
- `@contract`、`@step`、`@boundary`：函数契约
- 函数签名：只有签名，不实现具体逻辑（抛出 `throw new Error('Not implemented')`）

## 对话原则

1. **基于需求设计**：所有功能模块都应该来自需求文档
2. **避免过度设计**：不要设计用不到的命令和状态
3. **考虑可测试性**：设计应该便于单元测试
4. **保持简单**：优先使用简单的状态管理，避免复杂的状态机
5. **验证理解**：定期总结已设计的模块和命令，确保理解一致

## 输出格式

当所有 ViewModel 层设计完成后，输出设计文档和文件骨架。

设计文档结构参见 [OUTPUT-FORMAT.md](OUTPUT-FORMAT.md)。

## 特殊情况处理

### 当功能模块过多时
建议按业务领域分组，每个领域一个子目录。

### 当命令依赖复杂时
使用依赖注入模式，将依赖作为参数传入。

### 当状态管理复杂时
考虑使用状态管理库（Redux、Zustand、MobX 等）。

### 当循环依赖出现时
重新设计模块边界，提取共享逻辑到独立模块。

## 注意事项

- **必须标注 @intent**：每个文件都必须在顶部标注 @intent
- **依赖通过 import 声明**：不需要手动标注 @dependency，系统会自动从 import 语句中提取
- **ViewModel 层不依赖 View 层**：依赖方向是 View → ViewModel → Model
- **避免在 ViewModel 中写 UI 逻辑**：UI 逻辑应该在 View 层
- **保持命令简单**：复杂的业务逻辑应该在 Model 层的 Service 中
- **使用 @contract、@step、@boundary**：为所有函数标注契约

## 最终交付物

当所有 ViewModel 层设计完成后：

1. 将设计文档保存为 `.cdd/04-viewmodel-design.md`
2. 生成 ViewModel 层文件骨架到 `src/viewmodel/` 目录：
   - `src/viewmodel/commands/` - 命令处理器骨架
   - `src/viewmodel/context/` - 上下文管理器骨架
   - `src/viewmodel/roles/` - 角色/功能模块骨架
3. **每个文件都必须标注 @intent**
4. **每个函数都必须标注 @contract、@step、@boundary**
5. **依赖关系通过 import 语句声明**

该文档和代码将作为下一阶段（View/Chat 设计）的输入。

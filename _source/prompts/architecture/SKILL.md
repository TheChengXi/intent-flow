# 阶段 2：架构设计

基于需求文档（如果有），通过对话确定技术栈、编程语言和模块划分，输出架构设计文档。

## 前置依赖

**推荐读取**：`.cdd/01-requirements.md`（需求文档）

如果该文件不存在，可以直接根据用户描述进行架构设计。

**说明**：需求分析是推荐的但不是强制的。如果用户跳过了需求分析，可以在架构设计阶段通过对话了解需求。

## 工作流程

### 1. 识别项目类型

首先确定项目的基本类型：
- 这是什么类型的项目？（Web 应用、CLI 工具、库、服务端 API、桌面应用、VSCode 扩展等）
- 项目的运行环境是什么？（浏览器、Node.js、Electron、VSCode 等）

### 2. 确定技术栈

根据项目类型，询问或推荐技术栈：

**核心决策**：
- **编程语言**：TypeScript/JavaScript、Python、Go、Java、Rust、C# 等
- **运行环境**：浏览器、Node.js、Electron、VSCode、服务器等
- **核心框架**：React/Vue/Angular（前端）、Express/FastAPI/Gin（后端）等

**简单项目**：只需确定语言和基础框架即可

**复杂项目**：需要详细的技术栈选择

**Web 前端项目**：框架（React/Vue/Angular）、语言（TypeScript/JavaScript）、状态管理、UI 库

**后端 API 项目**：语言（Node.js/Python/Go/Java）、框架、数据库

**CLI 工具**：语言、CLI 框架

**VSCode 扩展**：TypeScript、VSCode Extension API

**全栈项目**：前端技术栈 + 后端技术栈 + 通信方式

### 3. 确定架构模式

**CCD 框架强制使用三层架构（基于六边形架构）**：

无论项目大小，都必须使用以下三层：

- **数据层（Data Layer）**：数据实体、仓库接口、数据源实现
- **应用层（Application Layer）**：用例、业务规则、应用服务
- **适配层（Adapter Layer）**：输入适配器（UI/API）、输出适配器（数据库/外部服务）

**依赖方向（硬性要求，严格单向）**：
```
适配层（Adapter Layer）
    ↓ 依赖
应用层（Application Layer）
    ↓ 依赖
数据层（Data Layer）
```

**禁止反向依赖**：
- 数据层不能依赖应用层
- 应用层不能依赖适配层
- 任何跨层通信都必须通过抽象接口（依赖倒置原则）

**为什么必须三层**：
- 即使是简单的 CRUD，也需要三层来保证清晰的职责分离
- 三层结构让代码易于测试、易于维护、易于扩展
- 在 AI 编程时代，清晰的架构比代码量更重要

### 4. 模块划分

根据需求文档中的核心功能，划分模块：

**简单项目**：
- 可以只有一个模块，但仍然需要三层结构
- 例如：一个 TODO 应用，只有一个 Todo 模块，但有 data/application/adapter 三层

**复杂项目**：
- 按业务领域划分模块（如：用户模块、订单模块、支付模块）
- 每个模块都有自己的三层结构

**询问或推荐**：
- 每个核心功能对应哪些模块？
- 模块的职责边界是什么？
- 模块之间如何通信？

**模块划分原则**：
- **单一职责**：每个模块只负责一件事
- **高内聚低耦合**：模块内部紧密相关，模块之间松散耦合
- **依赖方向**：适配层 → 应用层 → 数据层（严格单向依赖）

### 5. 确定模块通信方式

询问或推荐模块间的通信方式：

**层内通信（同一层的不同模块）**：
- **应用层 ↔ 应用层**：事件总线、共享上下文、依赖注入
- **数据层 ↔ 数据层**：直接调用（同层可以互相依赖）

**跨层通信（必须遵循依赖方向）**：
- **适配层 → 应用层**：调用用例/命令、传递 DTO
- **应用层 → 数据层**：调用仓库接口/数据服务
- **数据层 → 应用层**：通过回调接口（在应用层定义，数据层调用）
- **应用层 → 适配层**：通过事件发布（在应用层定义，适配层监听）

**跨层通信的核心原则**：
- 依赖倒置：高层定义接口，低层实现接口
- 禁止反向依赖：低层不能直接依赖高层的具体实现
- 参见 [WORKFLOW.md](../_shared/WORKFLOW.md) 中的跨层通信模式

### 6. 确定数据流向

确定数据在系统中的流向：
- 外部请求 → 适配层 → 应用层 → 数据层
- 数据层 → 应用层 → 适配层 → 外部响应
- 是否需要状态管理？
- 是否需要缓存？

## 对话原则

1. **基于需求推荐**：根据需求文档的复杂度推荐合适的技术栈
2. **考虑现有技术栈**：如果项目已有技术栈，优先沿用
3. **权衡利弊**：对于每个技术选择，说明优缺点
4. **避免过度设计**：不要为简单需求设计复杂架构
5. **预留扩展性**：为未来的扩展功能预留接口

## 输出格式

当所有架构决策确定后，输出架构设计文档到 `.cdd/02-architecture.md`。

文档结构参见 [OUTPUT-FORMAT.md](OUTPUT-FORMAT.md)。

## 特殊情况处理

### 当需求文档不完整时
提示用户回到需求分析阶段补充缺失的需求。

### 当用户不确定技术选型时
提供 2-3 个推荐方案，说明每个方案的优缺点和适用场景。

### 当架构过于复杂时
建议简化架构，优先实现核心功能，为扩展功能预留接口。

## 注意事项

- **不要设计数据模型**：数据模型将在下一阶段（数据层设计）进行
- **不要设计具体实现**：只设计架构层次和模块划分，不涉及具体代码
- **保持架构清晰**：确保每个模块的职责边界清晰
- **遵循依赖方向**：适配层 → 应用层 → 数据层（硬性要求，严格单向依赖）
- **考虑可测试性**：架构设计应便于单元测试和集成测试
- **三层是强制的**：任何项目都必须有数据层、应用层、适配层
- **跨层通信必须通过抽象**：禁止反向依赖，必须使用依赖倒置原则

## 最终交付物

将架构设计文档保存为 `.cdd/02-architecture.md`。

该文档将作为下一阶段（数据层设计）的输入。

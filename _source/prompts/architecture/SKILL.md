# 阶段 2：架构设计

基于需求文档，通过对话确定技术栈、架构模式和模块划分，输出架构设计文档。

## 前置依赖

**必须读取**：`.cdd/01-requirements.md`（需求文档）

如果该文件不存在，提示用户先完成需求分析阶段。

## 工作流程

### 1. 识别项目类型

首先确定项目的基本类型：
- 这是什么类型的项目？（Web 应用、CLI 工具、库、服务端 API、桌面应用、VSCode 扩展等）
- 项目的运行环境是什么？（浏览器、Node.js、Electron、VSCode 等）

### 2. 确定技术栈

根据项目类型，询问或推荐技术栈：

**Web 前端项目**：框架（React/Vue/Angular）、语言（TypeScript/JavaScript）、状态管理、UI 库

**后端 API 项目**：语言（Node.js/Python/Go/Java）、框架、数据库

**CLI 工具**：语言、CLI 框架

**VSCode 扩展**：TypeScript、VSCode Extension API

**全栈项目**：前端技术栈 + 后端技术栈 + 通信方式

### 3. 确定架构模式

根据项目类型和技术栈，推荐架构模式：

**常见架构模式**：
- **MVC**：适合传统 Web 应用
- **MVVM**：适合前端应用（React、Vue）
- **三层架构**（Model-ViewModel-View）：适合复杂前端应用
- **Clean Architecture**：适合大型后端项目
- **分层架构**：适合中小型后端项目
- **插件架构**：适合可扩展的工具

**对于 CCD 框架推荐的三层架构**：
- **Model 层**：数据实体、仓库、业务服务
- **ViewModel 层**：状态管理、用户操作处理、业务逻辑编排
- **View 层**：UI 组件、页面、交互界面

### 4. 模块划分

根据需求文档中的核心功能，划分模块：

**询问或推荐**：
- 每个核心功能对应哪些模块？
- 模块的职责边界是什么？
- 模块之间如何通信？

**模块划分原则**：
- **单一职责**：每个模块只负责一件事
- **高内聚低耦合**：模块内部紧密相关，模块之间松散耦合
- **依赖方向**：View → ViewModel → Model（单向依赖）

### 5. 确定模块通信方式

询问或推荐模块间的通信方式：
- **View → ViewModel**：事件/方法调用、Props 传递
- **ViewModel → Model**：服务/仓库接口调用
- **ViewModel ↔ ViewModel**：事件总线、共享状态、依赖注入

### 6. 确定数据流向

确定数据在系统中的流向：
- 用户输入 → View → ViewModel → Model
- Model → ViewModel → View → 用户界面
- 是否需要状态管理？
- 是否需要缓存？

## 对话原则

1. **基于需求推荐**：根据需求文档的复杂度推荐合适的技术栈
2. **考虑现有技术栈**：如果项目已有技术栈，优先沿用
3. **权衡利弊**：对于每个技术选择，说明优缺点
4. **避免过度设计**：不要为简单需求设计复杂架构
5. **预留扩展性**：为未来的扩展功能预留接口

## 输出格式

当所有架构决策确定后，输出架构设计文档到 `.cdd/02-architecture.md`。

文档结构参见 [OUTPUT-FORMAT.md](OUTPUT-FORMAT.md)。

## 特殊情况处理

### 当需求文档不完整时
提示用户回到需求分析阶段补充缺失的需求。

### 当用户不确定技术选型时
提供 2-3 个推荐方案，说明每个方案的优缺点和适用场景。

### 当架构过于复杂时
建议简化架构，优先实现核心功能，为扩展功能预留接口。

## 注意事项

- **不要设计数据模型**：数据模型将在下一阶段（Model 设计）进行
- **不要设计具体实现**：只设计架构层次和模块划分，不涉及具体代码
- **保持架构清晰**：确保每个模块的职责边界清晰
- **遵循依赖方向**：View → ViewModel → Model（单向依赖）
- **考虑可测试性**：架构设计应便于单元测试和集成测试

## 最终交付物

将架构设计文档保存为 `.cdd/02-architecture.md`。

该文档将作为下一阶段（Model 设计）的输入。

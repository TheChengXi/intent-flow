# Execute

以下规则具有最高优先级。

@intent 是写在每个文件头顶的交付规格（PRD），实现向规格对齐。

三阶段执行。Phase 2 期间不修改 @intent。

- 一：@intent 投射 → 主会话：每个文件头顶写入 @intent（新增创建 + 已有更新）
- 二：实现对齐 → 主会话 / 子进程：逐文件实现，向 Phase 1 的 @intent 对齐
- 三：集成验证 → 主会话：验证交付物符合预期，规格偏离时同步 @intent

---

## 阶段一：@intent 投射（主会话，唯一改 @intent 的窗口）

### 前置阅读

读取 [GLOSSARY.md](./GLOSSARY.md) 作为 @intent 质量的评判依据。

### 投射动作

#### 已有文件：更新 @intent

设计文档指定修改的已有文件，先更新其 @intent（规格先变，实现后跟）：
- git mv 再投射 @intent

```
project_intent(
  path: "src/.../SomeFile.ts",
  intent: "更新后的职责描述，反映新功能对该文件的影响",
  force: true
)
```

#### 新增文件：创建 @intent

设计文档指定新建的文件，直接创建：

```
project_intent(
  path: "src/.../NewFile.ts",
  intent: "根据设计文档写 @intent（职责 + 边界 + 验收条件）"
)
```

同时在新建文件中预留 part-to-later-on 的接口签名（实现留空或抛未实现错误）。

**完成标志**：所有涉及文件头顶的 @intent 构成完整的规格集合，与设计文档一致。

---

## 阶段二：实现对齐

按文件逐文件实现，向该文件头顶的 @intent 对齐。

按依赖方向（下层→上层）确定文件顺序。

### 执行模式判定

根据改动性质选择执行模式。此判定为强制路由，不是建议。

如果改动的 **正确性能用肉眼或类型系统验证** → **直接模式**
如果改动的 **正确性需要运行时行为验证** → **隔离 TDD**

#### 直接模式适用场景

- 改类型定义、接口签名
- 修配置错误
- 重命名、提取函数（纯重构，不改行为）
- 加简单胶水代码（CRUD 通路，无业务分支）
- 一次性脚本 / 原型代码

#### 隔离 TDD 适用场景

- 新增核心功能模块
- 跨文件的接口协调改动
- 复杂业务逻辑（多个分支、多个边界条件）
- 修复涉及行为验证的 bug

#### 模式 A：直接模式

读 @intent → 直接实现 → 跑验证确认通过。

不写单元测试，不改 @intent。

#### 模式 B：隔离 TDD

三 agent 隔离执行，上下文不互通，防止测试和实现共享盲点：

```
test-writer（写测试，看不到实现）
    → code-writer（写实现，看不到测试推理，只读接口签名）
    → reviewer（审查，先跑测试再审查规格对齐）
```

每轮针对一个文件。不满足 VERDICT: PASS 时，循环 code-writer → reviewer 最多 3 次。

**完成标志**：每个文件的实现满足其 @intent 规格，结果可验证。

---

## 阶段三：集成验证

所有文件实现完成后：

1. **集成验证** — 把各部分组合在一起，验证整体符合预期。验证方式按项目类型确定
2. **全量验证** — 所有可运行的验证通过
3. **重构** — 按需重构，每步后验证。调整文件职责时同步更新 @intent

规格偏离时（@intent 与实际需求不匹配，而非代码 bug）→ 先更新 @intent，再改实现。

执行完成后调用 report skill 生成关账报告。

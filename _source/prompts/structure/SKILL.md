# 阶段 1：需求分析

通过对话收集需求信息，输出结构化的需求文档。

## 前置依赖

无。这是设计流程的第一阶段。

## 工作流程

### 1. 理解整体意图

询问：
- 这个项目/功能的核心目标是什么？
- 主要解决什么问题？
- 面向什么用户群体？

**每次只问 1-3 个问题**，等待用户回答后再继续。

### 2. 探索功能边界

逐步细化功能范围：
- 有哪些主要功能模块？
- 每个模块负责什么？
- 模块之间如何协作？

**使用具体场景验证理解**：
- "如果用户想要 X，系统应该如何响应？"
- "当 Y 情况发生时，应该怎么处理？"

### 3. 确认业务规则

对于关键业务逻辑，询问：
- 计算逻辑如何实现？
- 数据验证规则是什么？
- 错误处理策略是什么？
- 边界条件是什么？

### 4. 确认非功能需求

询问性能、安全、可用性要求：
- 性能要求是什么？（响应时间、并发量等）
- 安全要求是什么？（认证、授权、数据加密等）
- 可用性要求是什么？（易用性、无障碍等）

### 5. 划分 MVP 范围

帮助用户识别核心功能和扩展功能：
- 哪些功能是第一版必须实现的？
- 哪些功能可以放到后续版本？

## 对话原则

1. **渐进式提问**：从大到小，从抽象到具体
2. **一次一个主题**：不要同时问多个不相关的问题
3. **提供推荐答案**：对于每个问题，给出你的建议
4. **使用具体场景**：用实际例子帮助用户思考
5. **验证理解**：定期总结已确认的内容，确保理解一致

## 输出格式

当所有信息收集完毕后，输出需求文档到 `.cdd/01-requirements.md`。

文档结构参见 [OUTPUT-FORMAT.md](OUTPUT-FORMAT.md)。

## 特殊情况处理

### 当用户需求过于模糊时
不要直接拒绝，而是：
1. 提供 2-3 个常见的实现方向
2. 询问用户更倾向于哪个方向
3. 根据选择继续细化

### 当用户需求过于复杂时
建议分阶段实现：
1. 识别核心功能（MVP）
2. 识别扩展功能
3. 建议先实现核心功能
4. 为扩展功能预留接口

## 注意事项

- **不要涉及技术实现**：只关注业务需求，不讨论技术栈、架构模式
- **不要假设未确认的需求**：不确定时一定要问
- **保持业务语言**：使用用户能理解的术语，避免过早技术化
- **关注业务规则**：重点澄清业务逻辑和边界条件
- **不要生成数据模型**：数据模型将在后续阶段设计
- **不要生成架构设计**：架构设计将在后续阶段进行

## 最终交付物

将需求文档保存为 `.cdd/01-requirements.md`。

该文档将作为下一阶段（架构设计）的输入。

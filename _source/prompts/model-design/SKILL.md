# 阶段 3：Model 层设计

基于需求文档和架构设计文档，通过对话设计数据实体、字段、关系，并生成 Model 层代码。

## 前置依赖

**必须读取**：
- `.cdd/01-requirements.md`（需求文档）
- `.cdd/02-architecture.md`（架构设计文档）

如果这些文件不存在，提示用户先完成前置阶段。

## 工作流程

### 1. 识别核心实体

从需求文档中识别核心业务实体：
- 哪些名词是系统的核心概念？（例如：用户、订单、商品、文章等）
- 哪些实体需要持久化存储？
- 哪些实体只是临时数据？

**询问用户确认**：
- "根据需求文档，我识别出以下核心实体：[实体1]、[实体2]、[实体3]，是否正确？"
- "是否还有其他实体需要添加？"

### 2. 设计实体字段

针对每个核心实体，逐一设计字段：

**询问或推荐**：
- 这个实体有哪些字段？
- 每个字段的类型是什么？（string、number、boolean、Date、enum 等）
- 哪些字段是必填的？
- 哪些字段有默认值？
- 字段的验证规则是什么？

**字段设计原则**：
- **最小化原则**：只包含必要的字段，避免冗余
- **类型明确**：使用明确的类型，避免 any
- **可空性明确**：明确哪些字段可以为 null/undefined
- **枚举优先**：对于固定取值的字段，使用枚举类型

### 3. 设计实体关系

确定实体之间的关系：

**关系类型**：
- **一对一**（1:1）：例如用户和用户配置
- **一对多**（1:N）：例如用户和订单
- **多对多**（M:N）：例如文章和标签

**询问或推荐**：
- [实体1] 和 [实体2] 是什么关系？
- 关系是单向的还是双向的？
- 关系是强制的还是可选的？

### 4. 设计数据仓库接口

为每个实体设计数据仓库（Repository）接口：

**基础 CRUD 操作**：
- `create(entity)`: 创建实体
- `findById(id)`: 根据 ID 查询
- `findAll()`: 查询所有
- `update(id, entity)`: 更新实体
- `delete(id)`: 删除实体

**自定义查询**：根据业务需求设计自定义查询方法

### 5. 设计业务服务

为复杂的业务逻辑设计服务（Service）：

**服务设计原则**：
- **单一职责**：每个服务只负责一类业务逻辑
- **无状态**：服务不应该持有状态
- **可测试**：服务应该易于单元测试

**常见服务类型**：
- **计算服务**：例如统计、聚合、排序
- **验证服务**：例如数据验证、业务规则验证
- **转换服务**：例如数据格式转换、映射
- **集成服务**：例如调用外部 API、文件操作

### 6. 生成 Model 层代码

根据设计生成 TypeScript 代码：

**生成内容**：
1. **实体定义**（`src/model/entities/`）：使用 `@entity` 标注
2. **数据仓库接口和实现**（`src/model/repositories/`）：使用 `@contract`、`@step`、`@boundary` 标注
3. **业务服务**（`src/model/services/`）：使用 `@contract`、`@step`、`@boundary` 标注

**代码规范**：
- 使用 TypeScript 严格模式
- 使用接口定义契约
- 使用 JSDoc 注释说明用途
- 遵循项目现有的代码风格
- **Model 层不需要标注 @intent**（因为是纯数据实体）

## 对话原则

1. **基于需求设计**：所有实体和字段都应该来自需求文档
2. **避免过度设计**：不要设计用不到的字段和关系
3. **考虑扩展性**：为未来的扩展功能预留接口
4. **保持简单**：优先使用简单的数据结构，避免复杂的嵌套
5. **验证理解**：定期总结已设计的实体和关系，确保理解一致

## 输出格式

当所有数据模型设计完成后，输出设计文档和代码。

设计文档结构参见 [OUTPUT-FORMAT.md](OUTPUT-FORMAT.md)。

## 特殊情况处理

### 当需求文档不明确时
回到需求分析阶段，补充缺失的业务规则和数据要求。

### 当实体关系复杂时
绘制实体关系图（ER 图），帮助用户理解实体之间的关系。

### 当字段过多时
建议拆分实体，遵循单一职责原则。

### 当存储方式不确定时
根据架构设计文档中的技术栈推荐存储方式：
- 简单项目：文件系统（JSON）
- 中型项目：SQLite、LocalStorage
- 大型项目：PostgreSQL、MySQL、MongoDB

## 注意事项

- **Model 层不包含 Intent**：Model 层是纯数据层，不需要标注 @intent
- **Model 层是纯数据层**：不包含 UI 逻辑、不依赖 ViewModel 和 View
- **保持实体简单**：实体只包含数据字段，不包含业务逻辑
- **业务逻辑在服务中**：复杂的业务逻辑应该在 Service 中实现
- **遵循依赖方向**：Model 层不依赖任何其他层
- **使用 @contract、@step、@boundary**：为所有函数标注契约

## 最终交付物

当所有数据模型设计完成后：

1. 将设计文档保存为 `.cdd/03-model-design.md`
2. 生成 Model 层代码到 `src/model/` 目录：
   - `src/model/entities/` - 实体定义（使用 @entity 标注）
   - `src/model/repositories/` - 数据仓库（使用 @contract、@step、@boundary 标注）
   - `src/model/services/` - 业务服务（使用 @contract、@step、@boundary 标注）

该文档和代码将作为下一阶段（ViewModel 设计）的输入。

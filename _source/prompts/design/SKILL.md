# 结构设计

以下规则具有最高优先级。

结构设计的目的是划定代码边界，防止无结构的单体文件。

## 核心规则

跨层依赖是 bug。结构设计阶段强制排除，不允许进入编码阶段。

依赖方向只有一种：上层可依赖下层，下层绝不能依赖上层，不允许跨层依赖。

如果项目已有自己的分层模式，跟随它的命名。

---

## 工作流程

### 1. 判断项目状态

- **新项目**（代码从无到有）→ 从零设计结构
- **已有项目**（有既有代码）→ 顺应原有结构，只做增量
- **拍板不了** → 联网搜索

### 2. 执行

#### 2a. 新项目 — 从零设计

分析需求中的核心功能，做模块划分：

- **上层**：处理用户交互、外部输入输出
- **中间层**：业务逻辑编排
- **下层**：数据存取、外部服务

依赖方向：上层 → 中间层 → 下层。下层绝不能反向依赖。

模块划分原则：每个模块只做一件事。
接口原则：只暴露必要的，隐藏实现细节。

完成后输出模块清单和依赖链。

#### 2b. 已有项目 — 顺应原有结构

1. **读原有结构**：先看项目现有的分层模式，无论叫什么名字，跟随它
2. **找落脚点**：新功能放在哪一层哪个模块
3. **验依赖**：新增依赖必须不跨层。原有结构中存在跨层依赖 → 在 design.md 中标明，作为本次一并修复项
4. **输出改动**：改动点清单 + 新增文件清单

#### 2c. 拍板不了 — 联网搜索

根据项目类型定向搜索：
- **前端项目** → 搜前端架构方案
- **后端项目** → 搜后端架构方案
- **小脚本/工具** → 简单分层即可，不过度设计

搜完后回到 2a 或 2b。

### 3. 产出

- `.cdd/<feature-name>/design.md` — 本次设计文档
- `.cdd/<feature-name>/later-on.md` — 后续想法备忘

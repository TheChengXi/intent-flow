# 高熵需求 — 执行规范

## 适用条件

仅当 SKILL.md 判定入口熵值为 HIGH 时，按本文档执行。

## 核心原则

从零开始，走完整的需求分析管道：联网探索 → 需求收集 → 核心提取 → 结构化。

## 执行步骤

### 步骤 0：联网搜索（可选）

询问用户是否需要先联网搜索同类方案或行业实践。
如需搜索，按 [web-search-standard.md](./web-search-standard.md) 执行。

### 步骤 1：需求收集

每轮最多问 2 个问题，等回答再继续。

目标信息：
- 核心目标：解决谁的什么问题？
- 用户群体：谁会用它？
- 核心功能：如果只能说出 3 个能力，是什么？
- 关键业务规则：有什么特殊的计算逻辑或约束？

对话原则：
- 从大到小：先全景，再细节
- 一次一个话题
- 提供推荐答案，不给纯开放提问
- 每轮结束做一句话总结

### 步骤 2：边界确认

记录用户提到的范围边界（要什么、不要什么），但不做压缩决策。

### 步骤 3：提取核心功能（最多 3 个）

从收集到的需求中提取 1～3 个不可再拆的核心能力。
用固定句式描述：

> **系统能够 + 动词 + 业务对象 + 关键约束**

回答：
- 这个需求最核心的业务价值在哪一环？
- 如果砍到只剩 1 个功能，留哪个？
- 核心功能之间是并列还是主+支撑？

### 步骤 4：分析功能间的结构关系

核心功能彼此的关系比每个功能本身更重要：

| 维度 | 要回答的问题 |
|------|------------|
| **依赖** | 功能 A 需要功能 B 的什么输出才能工作？ |
| **约束** | A 的规则会限制 B 的设计吗？ |
| **复用** | A 和 B 有没有共享的数据或逻辑？ |
| **冲突** | A 和 B 在某些场景下目标相反吗？怎么调和？ |

### 步骤 5：用场景验证关系

构造一条端到端用户场景，验证所有核心功能是否参与，依赖关系是否成立。

### 步骤 6：可选：范围压缩

如果用户需要，划定优先级线：
- **必须保留的**：缺少就转不动的核心功能和连接
- **可延后的**：标记延后理由

### 步骤 7：输出需求文档

按 [OUTPUT-FORMAT.md](./OUTPUT-FORMAT.md) 写入 `.cdd/01-requirements.md`。

告知用户需求分析完成，可以进入结构设计阶段。

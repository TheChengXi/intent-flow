# 需求分析

以下规则具有最高优先级。

需求分析是一个迭代收敛过程。
退出条件：需求清晰且可执行。不满足则继续下一轮。

---

## 核心循环

每轮从第 1 项开始，按需执行 2-4 项。不要求每轮全部执行，不要求固定顺序。

### 1. 信息收集与澄清

提问密度由信息缺口决定：
- 缺口大 → 多维度并行问
- 接近清晰 → 收尾问题

覆盖维度：
- 核心目标 = {解决谁的什么问题}
- 核心功能 = 至多 3 个
- 业务规则 = {计算逻辑、约束条件}

每轮结束时标记已确认清单 + 仍模糊清单。

### 2. 联网搜索（按需）

**触发**：主动判断以下场景，不询问用户"要不要搜"：

| 问题性质 | 搜索方向 |
|---------|---------|
| 共性问题（有成熟方案） | 搜别人怎么解决的、最佳实践 |
| creative | 搜同类项目做了什么、解决了什么 |
| 模糊概念 / 找灵感 | 扩大范围搜行为相似但不同领域的启发内容 |
| 任何上述场景 | 顺带搜踩坑记录和解决方案 |

### 3. 预设测试

根据当前理解，从用户视角写一个可执行的测试步骤：

> 操作：{用户做什么} → 预期结果：{系统应响应什么}

- 写得出来 → 需求已具备可执行性，测试方案作为交付物
- 写不出来 → 需求不够具体，回到第 1 项继续收集

### 4. 收束边界

每轮判断时间窗口：
- **此时必做**：缺少就转不动的
- **此时不做**：标记延后理由 + 什么条件下才需要做

不做"永远不做"的判断，只判断"此时"。

---

## 退出条件

同时满足 4 项才算清晰且可执行：

1. 核心目标无歧义，一句话可概括
2. 核心功能可列出（≤3 个），规则清晰
3. 至少一个预设测试方案可写可执行
4. 必做/延后边界已划定

不满足 → 继续下一轮。
满足后输出需求文档。

---

## 创建 Feature 目录

**命名规则**：以业务对象命名，不以手段/方法命名。

- ❌ 以手段命名：`repair-with-template-method`、`migrate-by-batch`
- ✅ 以对象命名：`tool-repair`、`database-migration`

生成 kebab-case 短名 → 展示确认。

确认后创建 `.cdd/<feature-name>/` 目录。

---

## 交付物

保存为 `.cdd/<feature-name>/requirement.md`，按以下格式输出：

```markdown
# 需求文档：[功能名称]

## 项目意图
[一句话描述核心目标]

## 功能清单
1. **[功能1]**：[一句话描述]
（列出所有识别到的功能，不做核心/非核心区分）

## 核心功能

### 核心功能1：[功能名称]
- **能力**：系统能够 + [动词] + [业务对象] + [关键约束]
- **业务价值**：[直接产生的业务成果]

### 核心功能2：[功能名称]
（最多 3 个，超出标记为扩展）

## 业务规则

### [规则名称]
- **场景**：[什么情况下触发]
- **行为**：[系统如何响应]
- **异常处理**：[异常情况怎么处理]

## 预设测试

> 从用户视角可执行的测试步骤，验证功能是否符合预期。

### 前置条件
[验证前需要准备什么：数据、环境、账号等]

### 测试步骤

1. **[操作]**：[用户做什么]
   **预期结果**：[系统应该出现什么]

### 异常场景

- **[异常情况]**：[操作] → [预期处理方式]

## 边界收束

**此时必做**：
- [缺少就转不动的]

**此时不做**：
- [延后项] — [延后理由 + 什么条件下才需要做]
```

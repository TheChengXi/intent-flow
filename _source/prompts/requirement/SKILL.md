# 需求分析

以下规则具有最高优先级。

两阶段管道：Phase 1 需求收集 → Phase 2 核心提取与结构分析。
Phase 2 依赖 Phase 1 的输出。

---

## Phase 1：需求收集

### 0. 命名 Feature（首次执行时）

当意图可概括为一句时 → 生成 kebab-case 名 → 展示确认。

1. **提炼核心意图**：用一句话概括这个 feature 要做什么
2. **生成 kebab-case 短名**：从核心意图提取 2-4 个关键词，连字符连接
   - "登录后查看历史记录" → `user-login-history`
   - 禁止使用泛词 `new-feature`、`my-feature`、`test`
3. **展示确认**：提议命名并确认
   - 拒绝 → 提供或重新提炼
   - 确认 → 创建 `.cdd/<feature-name>/` 目录

创建后本阶段所有产出写入 `.cdd/<feature-name>/` 目录。

### 0a. 联网搜索（可选）

触发联网搜索确认：是否需要先搜索同类方案？
- 是 → 按 [web-search-standard](./web-search-standard.md) 执行，结果作为参考背景
- 否 → 进入步骤 1

### 1. 了解全景

每轮最多 2 个问题，等回复后继续。

目标信息：
- 核心目标 = {解决谁的什么问题}
- 群体角色 = {使用者}
- 核心功能 = 至多 3 个能力
- 业务规则 = {计算逻辑或约束}

### 2. 用场景验证理解

选取 1-2 个场景，描述操作流程并请求确认：
- "操作流程是否 A → B → C？"
- "当 Y 发生时，系统怎么处理？"

### 3. 生成用户验证方案

根据已确认需求，生成非技术可执行的验证方案：

1. **草拟方案** — 围绕核心功能，编写按步骤执行的验证流程，每步包含操作和预期结果
2. **展示确认** — 展示并确认
   - 确认 → 归入交付物
   - 调整 → 修改后再次确认
   - 难以描述 → 从方案反向提炼需求，确认一致后更新方案
3. **覆盖异常** — 至少包含一条异常场景及其预期处理方式

> 方案不涉及代码、接口、数据库。只描述"操作什么 → 系统应响应什么"。

### 4. 确认边界

记录范围边界（要什么、不要什么），不做压缩决策。

**完成标志**：`.cdd/<feature-name>/requirement.md` 含项目意图、群体角色、功能清单（全部）、业务规则、用户验证方案。

## Phase 2：核心提取与结构分析

从需求中提取核心功能并分析结构关系。

### 前置条件

当以下任一条件成立时 → 调用 trace_dependency_chain：
- 目标文件超出当前知识范围
- 模块存在多个未知入口消费方
- 需验证依赖关系是否违反分层规则

否则 → 直接 Read 目标文件。

### 0. 声明分析角度

每项分析开始前声明：
- 切入角度 = {从什么视角分析}
- 选择理由 = {为什么这个角度合适}

确认后进入后续分析。

### 1. 识别核心功能（1-3 个）

从需求中提取不可再拆的核心能力。固定句式：

> 系统能够 + 动词 + 业务对象 + 关键约束

示例：`系统能够根据用户历史订单计算折扣，且折扣不低于成本价`

确认每个核心功能：
- 需求最核心的业务价值在哪一环？
- 如果只剩 1 个功能，留哪个？
- 核心功能之间是并列还是主+支撑？

### 2. 分析功能间的结构关系

四个维度：

| 维度 | 回答的问题 |
|------|-----------|
| 依赖 | 功能 A 需要功能 B 的什么输出？ |
| 约束 | A 的规则会限制 B 的设计吗？ |
| 复用 | A 和 B 共享什么数据或逻辑？ |
| 冲突 | A 和 B 目标相反吗？怎么调和？ |

### 3. 用场景验证关系

构造一个端到端场景，验证：
- 所有核心功能都参与
- 依赖关系成立
- 无隐藏功能未被识别

### 4. 可选：范围压缩

需要时划定优先级线：
- **必保项**：缺少就转不动的核心功能
- **可延后**：标记延后理由

**完成标志**：`.cdd/<feature-name>/requirement.md` 补充核心功能列表、关系矩阵、验证场景、用户验证方案。

## 对话约束

- Phase 1 执行顺序：全景 → 场景验证 → 验证方案 → 边界确认
- Phase 2 执行顺序：核心功能识别 → 关系分析 → 场景验证
- 每次完成一步后做一句话总结
- 描述不清晰时 → 主动改写并确认
- 不做技术实现（不分接口、不画 API、不涉及技术栈）
- 不假设未确认的信息
- 保持业务语言

## 特殊情况

### 需求发散无法收敛
提供 2-3 种核心解读角度确认。仍然发散则强制收敛，标记其余为待探索。

### 需求不清晰
先跑 /structure 收集完整需求再回来。

## 最终交付物

保存为 `.cdd/<feature-name>/requirement.md`，含：

1. 项目意图 & 群体角色
2. 功能清单（全部功能，Phase 1 产出）
3. 核心功能列表（Phase 2 补充）
4. 业务规则
5. 核心功能关系矩阵（依赖/约束/复用/冲突）
6. 验证场景（至少一个端到端场景）
7. 用户验证方案（按步骤执行的验收流程，每步含操作和预期结果；不涉及代码/接口/数据库）
8. 非功能需求（如提到）
9. 可选：范围压缩线

交付物可作为架构设计的核心输入。

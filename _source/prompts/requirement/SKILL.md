# 需求分析

以下规则具有最高优先级。

两阶段管道：Phase 1 需求收集 → Phase 2 核心提取与结构分析。
Phase 2 依赖 Phase 1 的输出 `.cdd/01-requirements.md`。
文件已存在时可直接从 Phase 2 开始。

---

## Phase 1：需求收集

将模糊想法展开为结构化需求。

### 0. 联网搜索（可选）

触发联网搜索确认：是否需要先搜索同类方案？
- 是 → 按 [web-search-standard](./web-search-standard.md) 执行，结果作为参考背景
- 否 → 直接进入步骤 1

### 1. 了解全景

每轮最多 2 个问题，等回复后继续。

目标信息：
- 核心目标 = {解决谁的什么问题}
- 用户群体 = {使用者角色}
- 核心功能 = 至多 3 个能力
- 关键业务规则 = {特殊计算逻辑或约束}

### 2. 用场景验证理解

选 1-2 个具体场景确认操作流程：
- "假设用户想 X，流程是不是 A → B → C？"
- "当 Y 发生时，系统怎么处理？"

### 3. 确认边界

记录范围边界（要什么、不要什么），不作压缩决策。

**完成标志**：`.cdd/01-requirements.md` 包含项目意图、用户群体、功能清单（全部功能）、业务规则。

## Phase 2：核心提取与结构分析

从需求中提取核心功能并分析结构关系。

执行前调用 trace_dependency_chain：
1. 目标文件超出当前知识范围
2. 模块存在多个未知入口消费方
3. 需验证依赖关系是否违反分层规则
以上均不满足时，直接 Read 目标文件。

### 1. 识别核心功能（1-3 个）

从需求中提取不可再拆的核心能力。固定句式：

> 系统能够 + 动词 + 业务对象 + 关键约束

示例：`系统能够根据用户历史订单计算折扣，且折扣不低于成本价`

回答：
- 需求最核心的业务价值在哪一环？
- 如果只剩 1 个功能，留哪个？
- 核心功能之间是并列还是主+支撑？

### 2. 分析功能间的结构关系

四个维度：

| 维度 | 回答的问题 |
|------|-----------|
| 依赖 | 功能 A 需要功能 B 的什么输出？ |
| 约束 | A 的规则会限制 B 的设计吗？ |
| 复用 | A 和 B 共享什么数据或逻辑？ |
| 冲突 | A 和 B 目标相反吗？怎么调和？ |

### 3. 用场景验证关系

构造一个端到端场景，验证：
- 所有核心功能都参与
- 依赖关系成立
- 无隐藏功能未被识别

### 4. 可选：范围压缩

需要时划定优先级线：
- **必保项**：缺少就转不动的核心功能
- **可延后**：标记延后理由

**完成标志**：`.cdd/01-requirements.md` 补充核心功能列表、关系矩阵、验证场景。

## 对话原则

1. **Phase 1 从大到小**：先全景再细节。
2. **Phase 2 由内向外**：先收敛核心再分析关系。
3. **一次一个话题**。
4. **每轮收敛**：每完成一步做一句话总结。
5. **主动重述**：描述不清晰时主动改写并确认。

## 注意事项

- **不做技术实现**——不分接口、不画 API、不涉及技术栈。
- **不假设未确认的信息**。
- **保持业务语言**。
- Phase 1 **不做核心提取和范围压缩**——聚焦"有什么"。
- Phase 2 **不做需求收集**——假设需求已存在，做提取和结构化。

## 特殊情况

### 需求发散无法收敛
提供 2-3 种核心解读角度确认。仍然发散则强制收敛，标记其余为待探索。

### 需求不清晰
先跑 /structure 收集完整需求再回来。

## 最终交付物

保存为 `.cdd/01-requirements.md`。

内容包含：
1. 项目意图 & 用户群体
2. 功能清单（全部功能，Phase 1 产出）
3. 核心功能列表（Phase 2 补充）
4. 业务规则
5. 核心功能关系矩阵（依赖/约束/复用/冲突）
6. 验证场景（至少一个端到端场景）
7. 非功能需求（如提到）
8. 可选：范围压缩线

交付物可作为架构设计的核心输入。

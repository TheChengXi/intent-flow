好的。逐一厘清，先给出结论，再解释为什么。

## 一、自然语言转译员

**初期不需要历史记录，不需要工作行能力。**

初期转译员只做一件事：把用户选中的自然语言需求，转译成规范的注释。它不需要记住上次转译了什么，因为每次需求都是独立的。它不需要工作行能力，因为它不读取代码——它只读取用户选中的文本，以及全局的 `PROJECT_SOUL.md` 和 `BUSINESS_RULES.md`（通过插件自动注入）。

**上下文范围：**
- 用户选中的需求文本
- 全局 `PROJECT_SOUL.md`
- 相关的 `BUSINESS_RULES.md` 条款（若需求涉及）

**输出：**
```typescript
// @contract: ...
// @step: ...
// @boundary: ...
```

**不需要的：**
- 历史记录（每次转译是独立的）
- 工作行识别（它不读代码，只读用户选中的文本）

## 二、编译器

**需要历史记录（仅不通过时），需要工作行能力（但可以选择用 `//#region` 还是用注释边界）。**

编译器的上下文分三层：

**第一层：当前工作行的注释（必需）**
- 如果不使用 `//#region`：上下文 = 从 `@contract` 开始，到 `@boundary` 结束的注释块。
- 如果使用 `//#region`：上下文 = 整个 `//#region CDD-WorkLine` 块内的注释部分。

**第二层：被引用函数的 `@contract`（必需）**
- 编译器解析当前注释中的函数调用，找到那些函数的 `@contract`，只读注释，不读实现。

**第三层：历史记录（条件必需）**
- 若上次编译被审查员打回 → **必须**加载审查员的反馈 + 上次编译的代码。
- 若上次编译通过 → 不需要加载上次的代码（但建议保留编译记录在 `WorkSchedule` 中，供未来追溯）。

**第四层：编译规范（必需）**
- 加载 `COMPILE_SPEC.md`。

**编译器的工作行范围：**

| 方案 | 上下文起始 | 上下文结束 | 优点 | 缺点 |
|:---|:---|:---|:---|:---|
| 使用 `//#region` | `//#region CDD-WorkLine` | `//#endregion CDD-WorkLine` | 视觉清晰，折叠友好 | 需要多写两行标记 |
| 不使用 `//#region` | `@contract` 注释 | `@boundary` 注释 | 更轻量，少写两行 | 没有视觉区块，全靠约定 |

**初期建议：先不使用 `//#region`，用注释边界即可。** 等插件能自举后，再加 `//#region` 支持作为增强。

## 三、代码审查员

**需要历史记录，需要工作行能力（和编译器一致）。**

审查员的上下文：

**第一层：当前工作行的完整内容（必需）**
- 从 `@contract` 到 `// @end` 的全部内容（注释 + 代码）。

**第二层：编译规范（必需）**
- 加载 `COMPILE_SPEC.md`。

**第三层：历史记录（必需）**
- 编译器的本次编译记录（从 `WorkSchedule` 中读取本次编译的依赖契约版本）。
- 上次审查结果（若存在）：上一次是“通过”还是“不通过”？若不通过，不通过的原因是什么？

**审查员的工作行范围：**

和编译器一致。如果用 `//#region`，就是整个 `//#region` 块；如果不用，就是从 `@contract` 到 `// @end`。

## 四、代码转译员

**需要工作行能力。历史记录：需要读取旧的 `@contract`（作为“锚点”），以防止反向同步时丢失设计意图。**

代码转译员的上下文：

**第一层：当前工作行的完整代码（必需）**
- 从 `//#region` 或 `@contract` 到 `// @end` 的代码部分。

**第二层：旧的 `@contract`（条件必需，作为“锚点”防止注释被代码污染）**

你问：“让他审查上一次的 contract，保证他勉强不要犯错，这样子会不会过于冗余？”

**不会冗余。这是“锚点”。**

如果代码转译员只看新代码，不看旧注释，它可能会把一个“性能优化”误读成“功能变更”，然后把旧注释里正确的业务规则覆盖掉。让它同时看到旧注释和新代码，它才能输出“同步报告”——明确告诉用户：旧注释的哪一步被新代码修改了，是优化还是功能变更。

**第三层：历史记录（建议包含）**
- 上次转译结果（若存在）：上次同步时，注释被更新成了什么？这能帮助转译员检测“代码是否在短时间内反复修改”。

**代码转译员的工作行范围：**

和编译器一致。它只负责当前工作行的代码 → 注释同步。

## 五、迭代规划师

**需要全局历史记录，不需要工作行能力。**

迭代规划师的上下文：

**第一层：CHANGELOG.md（必需）**
- 了解所有历史变更。

**第二层：WorkSchedule.md（必需，但可轻量化）**

你说得对，随着工程扩展，WorkSchedule 会越来越长。初期不需要自动归档，但需要做两个轻量处理：
1. 迭代规划师只读取最近 N 条记录（如最近 50 条，或最近一周的记录）。
2. 当用户触发“检查契约过期”时，才做全量扫描（由代码转译员·守夜人模式执行）。

**第三层：上次迭代规划（建议询问）**

你提的“询问用户需不需要读取上一次的迭代规划”是对的。迭代规划师应该：
1. 先检查是否存在上次的迭代规划记录。
2. 若存在，输出：“检测到上次迭代规划（日期：xxx）。是否需要读取？”
3. 用户确认后再加载。

**迭代规划师不需要工作行能力。**

它不做代码级别的操作，只做变更影响分析和角色调度。

## 六、编译器与代码转译员是“一行工具”

你最后那句话，恰好是CDD“上下文最小化”原则的精确落地：

> “他们需要标识，只负责读取他们当前工作行内部的信息，其他工作行的也只读取它的父级和子级的注释。”

**对。这就是CDD的上下文硬约束。**

- **编译器**：只读取当前工作行的注释 + 被引用函数的 `@contract`（父与子）。
- **代码转译员**：只读取当前工作行的代码 + 旧的 `@contract`（如果有）。
- **审查员**：只读取当前工作行的注释 + 代码 + 编译规范。

它们都不会去读整个文件，不会去读无关模块的实现。这就是你设计的“一行工具”——它们是为这一行服务的，也只服务这一行。

---

## 七、总结：各 Agent 上下文管理表

| Agent | 工作行能力 | 历史记录 | 注释/代码读取范围 |
|:---|:---|:---|:---|
| 自然语言转译员 | 不需要 | 不需要 | 用户选中文本 + 全局 `_source/` 文件 |
| 编译器 | 需要 | 不通过时加载审查反馈 + 上次代码 | 当前工作行注释 + 被引用的 `@contract` |
| 代码审查员 | 需要 | 编译记录 + 上次审查结果 | 当前工作行完整内容（注释+代码） |
| 代码转译员 | 需要 | 旧 `@contract`（锚点） + 上次转译结果（可选） | 当前工作行代码 + 旧注释 |
| 迭代规划师 | 不需要 | CHANGELOG + WorkSchedule（可轻量）+ 上次规划（询问） | 全局 `_source/` 文件 |

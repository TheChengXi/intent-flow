# Execute

以下规则具有最高优先级。

@intent 是写在每个文件头顶的交付规格。

三阶段执行。Phase 2 期间不修改 @intent。

- 一：@intent 投射 → 主会话：每个文件头顶写入 @intent（新增创建 + 已有更新）
- 二：实现对齐 → 主会话 / 子进程：逐文件实现，向 Phase 1 的 @intent 对齐
- 三：集成验证 → 主会话：验证交付物符合预期，规格偏离时同步 @intent

---

## 阶段一：@intent 投射（主会话，唯一改 @intent 的窗口）

### 前置阅读

读取 [GLOSSARY.md](./GLOSSARY.md) 作为 @intent 质量的评判依据。

### 投射动作

#### 已有文件：更新 @intent

设计文档指定修改的已有文件，先更新其 @intent（规格先变，实现后跟）：
- git mv 再投射 @intent

#### 新增文件：创建 @intent

设计文档指定新建的文件，直接创建：

同时在新建文件中预留 part-to-later-on 的接口签名（实现留空或抛未实现错误）。

**完成标志**：所有涉及文件头顶的 @intent 构成完整的规格集合，与设计文档一致。

---

## 阶段二：实现对齐

按文件逐文件实现，向该文件头顶的 @intent 对齐。

按依赖方向（下层→上层）确定文件顺序。

### 执行模式判定

根据改动性质选择执行模式。此判定为强制路由，不是建议。

如果改动的 **正确性能用肉眼或类型系统验证** → **直接模式**
如果改动的 **正确性需要运行时行为验证** → **隔离 TDD**

#### 模式 A：直接模式

读 @intent → 直接实现 → 跑验证确认通过。

#### 模式 B：隔离 TDD

```
test-writer（写测试，看不到实现）
    → code-writer（写实现，对照测试）
    → 主会话审查（跑测试 + 核对 @intent 验收条件）
```

每轮针对一个文件。主会话审查不通过时，循环 code-writer 最多 3 次（轮次由主会话自己维护，不跨 agent 传递）。

**子 agent 交付物验证**：test-writer / code-writer 的交付物是 `logs/` 下的报告文件（test-report.md / code-report.md）。主会话**以文件为准**验证完成——文件存在且内容完整即视为已交付，工具返回文本丢失/缺失不视为未完成。

**完成标志**：每个文件的实现满足其 @intent 规格，结果可验证。

---

## 阶段三：集成验证

所有文件实现完成后：

1. **集成验证** — 把各部分组合在一起，验证整体符合预期。验证方式按项目类型确定
2. **全量验证** — 所有可运行的验证通过
3. **稳定性验证** — 全量测试循环跑 3 次，任一次失败即未通过；修复后重新循环
4. **重构** — 按需重构，每步后验证。调整文件职责时同步更新 @intent。重构后全量测试必须仍全绿，并再循环 3 次确认稳定。

执行完成后调用 report skill 生成关账报告。

# 核心提取与结构分析

把一个需求拆开，找出骨头。做提取和结构化。

在以下情况建议使用 trace_dependency_chain：
1. 你要修改的文件是你的知识边界之外的
2. 你不确定某个模块还有没有其他入口消费它
3. 你要验证依赖关系是否违反分层规则
如果以上都不符合，直接 Read 目标文件即可。

如果用户还没有明确的需求描述，建议先跑 `/structure`。

## 工作流程

### 0. 联网搜索（可选）

在提取核心功能前，询问用户：

> **是否需要先联网搜索一下同类方案或行业实践？**

如果用户确认，按 [web-search-standard](./web-search-standard.md) 执行搜索，
搜索结果作为核心分析的参考背景。

如果用户不需要，直接进入步骤 1。

### 1. 识别核心功能（最多 3 个）

从需求里提取 1～3 个不可再拆的核心能力。用固定句式精准描述：

> **系统能够 + 动词 + 业务对象 + 关键约束**

例子：`系统能够根据用户历史订单计算折扣，且折扣不低于成本价`。

回答这些问题：
- 这个需求最核心的**业务价值**在哪一环？
- 如果砍到只剩 1 个功能，留哪个？
- 核心功能之间是**并列**还是**主 + 支撑**？

### 2. 分析功能间的结构关系

核心功能彼此的关系比每个功能本身更重要：

| 维度 | 要回答的问题 |
|------|------------|
| **依赖** | 功能 A 需要功能 B 的什么输出才能工作？ |
| **约束** | A 的规则会限制 B 的设计吗？ |
| **复用** | A 和 B 有没有共享的数据或逻辑？ |
| **冲突** | A 和 B 在某些场景下目标相反吗？怎么调和？ |

### 3. 用场景验证关系

构造一条端到端用户场景，验证：
- 场景下所有核心功能都参与了吗？
- 场景走通时，功能间的依赖关系是否成立？
- 有没有隐藏的功能没被识别出来？

### 4. 可选：压缩范围

如果用户需要，可以基于以上结构划定优先级线：

- **必须保留的**：缺少就转不动的核心功能和连接
- **可延后的**：标记延后理由

如果不做范围压缩，输出到步骤 3 即可。

## 对话原则

1. **由内向外**：先收敛核心，再分析关系
2. **一次一个功能**：分析关系时，一次只围绕一个核心展开
3. **用场景验证**：每个核心功能至少用一个场景确认理解
4. **主动重述**：当发现描述不清晰时，主动给出改写并请用户确认
5. **每轮收敛**：每完成一个关系分析，做一句话总结

## 特殊情况处理

### 需求发散，无法收敛为核心
提供 2～3 种不同的核心解读角度，请用户确认最贴近目标的一个。仍然发散则强制收敛，标记其余为待探索。

### 需求本身就不清晰
建议先跑 `/structure` 收集完整需求，再回来做核心提取。

## 注意事项

- **不做需求收集**——假设需求已存在，做提取和结构化
- **不涉及技术实现**——不分接口、不画 API
- **不假设未确认的信息**
- **保持业务语言**
- **MVP 是可选项，不是必有输出**

## 最终交付物

保存为 `.cdd/01-requirements.md`。

文档包含：
- 核心功能列表（每个功能一句话 + 关键约束）
- 核心功能关系矩阵（依赖 / 约束 / 复用 / 冲突）
- 验证场景（至少一个端到端场景）
- 可选：范围压缩线（如果要了范围决策的话）

交付物可作为架构设计的核心输入。

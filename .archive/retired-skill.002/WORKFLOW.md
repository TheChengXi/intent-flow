# CCD 框架工作流程

## 核心原则

1. **需求分析是推荐的**：默认假设用户不完全了解自己的需求，需求分析帮助理清思路（但用户可以选择跳过）
2. **三层架构是强制的**：只要有需求，就必须是数据层、应用层、适配层三层并存
3. **依赖方向是硬性的**：适配层 → 应用层 → 数据层，严格单向，不可反向
4. **跨层通信必须通过抽象**：任何跨层需求都必须通过接口（依赖倒置原则）

## 整体流程概览

```
阶段 1: 需求分析 (/structure) [推荐]
  输出：.cdd/01-requirements.md
  说明：帮助用户理清需求，可跳过但强烈推荐
  
阶段 2: 架构设计 (/architecture) [必需]
  输入：需求文档（如果有）
  输出：.cdd/02-architecture.md（技术栈、语言选择、模块划分）
  说明：简单项目只需确定技术栈，复杂项目需要详细的模块划分
  
阶段 3: 数据层设计 (/data) [必需]
  输入：需求文档 + 架构文档
  输出：
    - .cdd/03-data-layer.md（详细设计文档）
    - src/data/**/*.{ext}（接口定义，根据架构文档中的语言生成）
  
阶段 4: 应用层设计 (/application) [必需]
  输入：需求文档 + 架构文档 + 数据层设计
  输出：
    - .cdd/04-application-layer.md（详细设计文档）
    - src/application/**/*.{ext}（类定义 + 方法签名）
  
阶段 5: 适配层设计 (/adapter) [必需]
  输入：需求文档 + 架构文档 + 应用层设计
  输出：
    - .cdd/05-adapter-layer.md（详细设计文档）
    - src/adapter/**/*.{ext}（类定义 + 方法签名）

---分界线：设计阶段结束，进入实现阶段---

阶段 6: 需求转译（右键工具）
  输入：选中的文件 + 对应的设计文档
  输出：添加 @contract、@step、@boundary 注释的文件
  工具：右键 → "CDD: 需求转译为注释"
  
阶段 7: 代码编译（右键工具）
  输入：带有 CDD 注释的文件
  输出：完整实现代码
  工具：右键 → "CDD: 编译注释为代码"
```

## 依赖关系

```
适配层 → 应用层 → 数据层
  ↓         ↓         ↓
 设计     设计      设计
  ↓         ↓         ↓
 转译     转译      转译
  ↓         ↓         ↓
 编译     编译      编译
```

**严格单向依赖（硬性要求）**：
- 适配层可以依赖应用层
- 应用层可以依赖数据层
- 数据层不依赖任何层（最底层）
- **禁止反向依赖**：数据层不能依赖应用层，应用层不能依赖适配层

**跨层通信规则**：
- 如果数据层需要"通知"适配层 → 在应用层定义回调接口，适配层实现，数据层通过应用层调用
- 如果应用层需要"通知"适配层 → 在应用层定义事件接口，适配层实现监听器
- 核心原则：**依赖倒置**，高层定义接口，低层实现接口

**为什么必须三层并存**：
- 即使是简单的 CRUD，也需要三层来保证清晰的职责分离
- 数据层：管理数据持久化
- 应用层：管理业务规则和流程编排
- 适配层：管理外部交互和数据转换
- 三层结构让代码易于测试、易于维护、易于扩展

## 实现顺序

**推荐顺序**：自底向上
1. 先实现数据层（设计 → 转译 → 编译）
2. 再实现应用层（设计 → 转译 → 编译）
3. 最后实现适配层（设计 → 转译 → 编译）

**原因**：
- 应用层需要 import 已实现的数据层接口
- 适配层需要 import 已实现的应用层类

## 设计阶段的职责

**只生成**：
- 接口定义（interface/protocol/trait）
- 类型定义（type/struct/class）
- 方法签名（无实现）
- @intent 注释（文件级别）
- import/require/using 语句

**不生成**：
- @contract、@step、@boundary 注释
- 具体实现代码
- 辅助方法

## 转译阶段的职责

**基于**：
- 接口定义
- 设计文档（详细的实现要点）

**生成**：
- 实现类骨架
- @contract、@step、@boundary 注释
- 构造函数（基于依赖推断）
- 方法签名（保持不变）

**不生成**：
- 具体实现代码

## 编译阶段的职责

**基于**：
- CDD 注释（@contract、@step、@boundary）

**生成**：
- 完整实现代码
- 辅助方法（验证、映射等）
- 错误处理逻辑
- 日志记录

## 关键原则

1. **每个阶段只做自己该做的事**：不越权，不脑补
2. **接口优先**：先定义契约，再实现细节
3. **文档驱动**：设计文档要足够详细，能支撑后续转译
4. **语言自适应**：根据架构文档中的语言选择生成对应语法
5. **严格分离**：设计、转译、编译三个阶段严格分离
6. **三层强制**：任何项目都必须有数据层、应用层、适配层
7. **依赖倒置**：跨层通信必须通过抽象接口，不允许反向依赖

## 跨层通信模式

### 模式 1：回调接口（数据层 → 应用层 → 适配层）

**场景**：数据层需要通知上层某个事件（如：数据变化、操作完成）

**实现**：
1. 在应用层定义回调接口
2. 数据层接受回调接口作为依赖
3. 适配层实现回调接口并注入到应用层

**示例**：
```
数据层：接受 DataChangeListener 接口
应用层：定义 DataChangeListener 接口
适配层：实现 DataChangeListener，注入到应用层
```

### 模式 2：事件总线（应用层 → 适配层）

**场景**：应用层需要通知适配层某个业务事件（如：订单创建、用户登录）

**实现**：
1. 在应用层定义事件接口和事件发布器
2. 适配层实现事件监听器
3. 应用层发布事件，适配层监听并响应

**示例**：
```
应用层：定义 OrderCreatedEvent 和 EventPublisher
适配层：实现 OrderCreatedEventListener
应用层：发布事件 → 适配层：监听并发送通知邮件
```

### 模式 3：依赖注入（所有层）

**场景**：任何层需要使用其他层的功能

**实现**：
1. 低层定义接口
2. 高层实现接口
3. 通过构造函数或方法参数注入

**示例**：
```
数据层：定义 UserRepository 接口
应用层：依赖 UserRepository 接口（不关心实现）
适配层：实现 UserRepository 接口（如：PostgresUserRepository）
```

# 阶段 5：适配层设计（Adapter Layer Design）

基于前置阶段的文档，通过对话设计适配层的输入适配器（UI/API）、输出适配器、交互逻辑，并生成文件骨架。

## 前置依赖

**必须读取**：
- `.cdd/01-requirements.md`（需求文档）
- `.cdd/02-architecture.md`（架构设计文档）
- `.cdd/03-data-layer.md`（数据层设计文档）
- `.cdd/04-application-layer.md`（应用层设计文档）

如果这些文件不存在，提示用户先完成前置阶段。

## 核心概念

参见 [GLOSSARY.md](../_shared//GLOSSARY.md) 中的术语定义：
- **@intent**：描述文件功能（必须标注）
- **@dependency**：通过 import 语句自动提取（不需要手动标注）

## 工作流程

### 1. 识别适配器类型

根据架构设计文档，确定项目需要的适配器类型：

**输入适配器（Input Adapters）**：
- **Web UI**：React/Vue 组件、页面
- **REST API**：Controller、路由处理器
- **GraphQL API**：Resolver
- **CLI**：命令行参数解析、交互
- **Chat 界面**：对话处理器、消息解析
- **VSCode 扩展**：Command、Webview、TreeView
- **消息队列**：消息消费者、事件监听器

**输出适配器（Output Adapters）**：
- **数据库实现**：Repository 的具体实现
- **外部 API 调用**：第三方服务集成
- **文件系统**：文件读写操作
- **缓存实现**：Redis、内存缓存

**询问用户确认**：
- "根据架构设计，需要以下适配器：[适配器列表]，是否正确？"
- "是否还有其他适配器需要添加？"

### 2. 设计输入适配器

针对每个输入适配器，设计接口契约和交互逻辑：

**Web UI 适配器**：
- 需要哪些页面/组件？
- 用户可以执行哪些操作？
- 如何调用应用层用例？
- 如何展示结果和错误？

**API 适配器**：
- 需要哪些端点（Endpoint）？
- 请求/响应格式是什么？
- 如何验证输入？
- 如何处理认证和授权？

**CLI 适配器**：
- 需要哪些命令？
- 每个命令的参数？
- 如何显示输出？

**交互设计原则**：
- **用户友好**：操作简单直观
- **即时反馈**：操作后立即给出反馈
- **错误提示**：清晰的错误提示和恢复建议
- **输入验证**：在边界处验证所有输入

### 3. 设计输出适配器

针对每个输出适配器，设计实现细节：

**数据库适配器**：
- 使用什么数据库？（PostgreSQL、MongoDB、SQLite）
- 如何实现 Repository 接口？
- 连接配置如何管理？

**外部 API 适配器**：
- 调用哪些外部服务？
- 如何处理认证？
- 如何处理超时和重试？

**文件系统适配器**：
- 文件存储在哪里？
- 文件格式是什么？
- 如何处理并发访问？

### 4. 设计数据转换

确定适配层如何转换数据格式：

**DTO（Data Transfer Object）设计**：
- 输入 DTO：外部格式 → 应用层格式
- 输出 DTO：应用层格式 → 外部格式

**转换原则**：
- **边界验证**：在适配层验证所有外部输入
- **格式转换**：处理不同的数据格式（JSON、XML、Protobuf）
- **错误映射**：将应用层错误映射为适配层错误格式

### 5. 设计组件层次

将适配层组织成清晰的结构：

**组件分类**：
- **输入适配器**：处理外部请求
- **输出适配器**：实现外部依赖
- **DTO/映射器**：数据格式转换
- **工具函数**：通用辅助功能

### 6. 生成接口定义

根据设计生成接口定义：

**生成内容**：
1. **输入适配器**（`src/adapter/input/`）：UI 组件、API Controller、CLI Handler、Chat Handler
2. **输出适配器**（`src/adapter/output/`）：数据库实现、外部 API 客户端、文件系统操作
3. **DTO/映射器**（`src/adapter/dto/`）：数据传输对象和转换函数
4. **工具函数**（`src/adapter/utils/`）：通用辅助功能


**代码规范**：
- 每个文件顶部添加 @intent 注释（使用目标语言的注释风格）
- 使用目标语言的依赖声明语法
- 只生成类型定义和方法签名
- 方法体为空实现或抛出未实现错误（根据目标语言习惯）

## 对话原则

1. **基于需求设计**：所有适配器都应该来自需求文档和架构设计
2. **避免过度设计**：不要设计用不到的适配器
3. **考虑用户体验**：输入适配器应该简洁、直观、易用
4. **保持一致性**：接口风格和错误处理应该一致
5. **验证理解**：定期总结已设计的适配器，确保理解一致

## 输出格式

当所有适配层设计完成后，输出设计文档和文件骨架。

设计文档结构参见 [OUTPUT-FORMAT.md](OUTPUT-FORMAT.md)。

## 特殊情况处理

### 当适配器过于复杂时
建议拆分成多个小适配器，每个适配器负责一个功能。

### 当需要实时更新时
考虑使用 WebSocket、轮询或事件监听机制。

### 当需要离线支持时
考虑使用 Service Worker、LocalStorage 或 IndexedDB。

### 当外部依赖不稳定时
实现重试机制、熔断器、降级策略。

## 注意事项

- **必须标注 @intent**：每个文件都必须在顶部标注 @intent
- **依赖通过 import 声明**：使用目标语言的依赖声明语法
- **适配层不直接依赖数据层**：必须通过应用层访问数据（硬性要求）
- **保持适配器简单**：复杂的逻辑应该在应用层处理
- **边界验证**：在适配层验证所有外部输入
- **错误处理要友好**：给出清晰的错误提示和恢复建议
- **设计阶段不生成 CDD 注释**：@contract、@step、@boundary 将在需求转译阶段生成
- **依赖倒置**：适配层实现应用层定义的接口（如：事件监听器、回调接口）
- **跨层通信**：适配层只能通过应用层的公开接口与数据层交互

## 最终交付物

当所有适配层设计完成后：

1. 将设计文档保存为 `.cdd/05-adapter-layer.md`
2. 生成适配层接口定义到相应目录：
   - `src/adapter/input/` - 输入适配器接口
   - `src/adapter/output/` - 输出适配器接口
   - `src/adapter/dto/` - DTO 和映射器接口
3. **每个文件都必须标注 @intent**
4. **依赖关系通过目标语言的依赖声明语法**
5. **只生成接口定义和方法签名，不生成实现代码**

至此，整个项目的五个阶段设计全部完成：
- 需求分析 → 架构设计 → 数据层设计 → 应用层设计 → 适配层设计

项目可以进入实现阶段（需求转译 → 代码编译）。

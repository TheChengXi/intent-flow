# CCD 框架工作流程

## 整体流程概览

```
阶段 1: 需求分析 (/structure)
  输出：.cdd/01-requirements.md
  
阶段 2: 架构设计 (/architecture)
  输入：需求文档
  输出：.cdd/02-architecture.md（包含技术栈、语言选择）
  
阶段 3: 数据层设计 (/data)
  输入：需求文档 + 架构文档
  输出：
    - .cdd/03-data-layer.md（详细设计文档）
    - src/data/**/*.{ext}（接口定义，根据架构文档中的语言生成）
  
阶段 4: 应用层设计 (/application)
  输入：需求文档 + 架构文档 + 数据层设计
  输出：
    - .cdd/04-application-layer.md（详细设计文档）
    - src/application/**/*.{ext}（类定义 + 方法签名）
  
阶段 5: 适配层设计 (/adapter)
  输入：需求文档 + 架构文档 + 应用层设计
  输出：
    - .cdd/05-adapter-layer.md（详细设计文档）
    - src/adapter/**/*.{ext}（类定义 + 方法签名）

---分界线：设计阶段结束，进入实现阶段---

阶段 6: 需求转译（右键工具）
  输入：选中的文件 + 对应的设计文档
  输出：添加 @contract、@step、@boundary 注释的文件
  工具：右键 → "CDD: 需求转译为注释"
  
阶段 7: 代码编译（右键工具）
  输入：带有 CDD 注释的文件
  输出：完整实现代码
  工具：右键 → "CDD: 编译注释为代码"
```

## 依赖关系

```
适配层 → 应用层 → 数据层
  ↓         ↓         ↓
 设计     设计      设计
  ↓         ↓         ↓
 转译     转译      转译
  ↓         ↓         ↓
 编译     编译      编译
```

**严格单向依赖**：
- 适配层可以依赖应用层
- 应用层可以依赖数据层
- 数据层不依赖任何层（最底层）

## 实现顺序

**推荐顺序**：自底向上
1. 先实现数据层（设计 → 转译 → 编译）
2. 再实现应用层（设计 → 转译 → 编译）
3. 最后实现适配层（设计 → 转译 → 编译）

**原因**：
- 应用层需要 import 已实现的数据层接口
- 适配层需要 import 已实现的应用层类

## 设计阶段的职责

**只生成**：
- 接口定义（interface/protocol/trait）
- 类型定义（type/struct/class）
- 方法签名（无实现）
- @intent 注释（文件级别）
- import/require/using 语句

**不生成**：
- @contract、@step、@boundary 注释
- 具体实现代码
- 辅助方法

## 转译阶段的职责

**基于**：
- 接口定义
- 设计文档（详细的实现要点）

**生成**：
- 实现类骨架
- @contract、@step、@boundary 注释
- 构造函数（基于依赖推断）
- 方法签名（保持不变）

**不生成**：
- 具体实现代码

## 编译阶段的职责

**基于**：
- CDD 注释（@contract、@step、@boundary）

**生成**：
- 完整实现代码
- 辅助方法（验证、映射等）
- 错误处理逻辑
- 日志记录

## 关键原则

1. **每个阶段只做自己该做的事**：不越权，不脑补
2. **接口优先**：先定义契约，再实现细节
3. **文档驱动**：设计文档要足够详细，能支撑后续转译
4. **语言自适应**：根据架构文档中的语言选择生成对应语法
5. **严格分离**：设计、转译、编译三个阶段严格分离

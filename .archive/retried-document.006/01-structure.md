# 核心提取：intentPackage 意图打包系统

## 核心功能

### ① 聚类生成引擎（主能力）
> **系统能够** 接收一个文件夹的所有 `@intent` + 内部依赖关系，调用 LLM 识别语义簇，输出结构化意图包（含 groups 分组、高层摘要、文件映射和 cross_refs）。

- **关键约束**：一次只消化单个文件夹，不强跨包聚合
- **定位**：纯函数——你喂什么，它吐什么；不碰文件系统、不决策覆盖
- **输出格式**：YAML + 哈希指纹 + groups 分组

### ② 增量维护（支撑 ①）
> **系统能够** 通过哈希指纹检测 `@intent` 变更，调用 ① 重算受影响的包，并在 pinned 或 LLM 失败时保留旧包。

- **关键约束**：O(变更文件夹数)，不扫描全局
- **扩展职责**："检测变更 → 触发重算 → 原子覆盖或降级保留"——所有"是否覆盖包文件"的决策在此集中
- **三个覆盖分支**：哈希不变→不做；哈希变+pinned→报警不覆盖；哈希变+未pinned+①成功→覆盖；①失败→保留旧包+告警
- **附加职责**：弃用检测（引用文件全部删除→deprecate）

### ③ 结构化访问（支撑 ① + ②）
> **系统能够** 通过 MCP 工具向开发者和 AI 提供意图包的结构化数据，屏蔽内部细节，管理废弃与关联。

- **关键约束**：AI 只能通过工具间接读取，不直接暴露文件系统
- **定位**：只读消费者，只管读文件+屏蔽+返回，不关心文件是怎么来的
- **可选的 stale 标记**：若读取时发现 hash 与当前 @intent 不匹配，可加 stale: true 标记

## 核心功能关系矩阵

### ① ↔ ②

| 维度 | 关系 |
|------|------|
| **依赖** | ② 调用 ①。② 做覆盖决策，① 只做聚类 |
| **约束** | pinned 是 ② 加给 ① 的执行锁（"就算 hash 变了也不触发重算"） |
| **复用** | 共享同一套 LLM prompt 和聚类逻辑 |
| **冲突** | 无。pinned 和 LLM 失败的保留策略本质上都是"② 决策这一次不覆盖" |

### ① ↔ ③

| 维度 | 关系 |
|------|------|
| **依赖** | ③ 消费 ① 的输出。没有包文件则无内容可提供 |
| **约束** | ① 的聚类稳定性影响 cross_refs 的可信度。若同个文件夹每次聚类分组不同，跨包引用可能断裂 |
| **复用** | 共享包的数据结构定义（package name, groups, files 等字段模型） |
| **冲突** | ① 写入内部字段（hash/pinned/deprecated），③ 要对外屏蔽。需要一个"内存储 vs 外视图"的字段分离 |

### ② ↔ ③

| 维度 | 关系 |
|------|------|
| **依赖** | ③ 依赖 ② 确保包新鲜。② 失效的包如果未被重算，③ 返回的是过期数据 |
| **约束** | ② 的废弃标记直接筛选 ③ 的返回内容——deprecated 的包不返回 |
| **复用** | 共享 `.cdd/packages/` 目录的文件读写接口 |
| **冲突** | 无直接冲突 |

### 关系结构图

```
  ① 聚类生成引擎 (纯函数)
    │
    │ ② 调用 ① 重算
    ▼
  ② 增量维护 (覆盖决策者)
    │
    ├── 成功 → 原子覆盖包文件
    ├── 失败 → 保留旧包 + 告警
    └── pinned → 报警不覆盖
    │
    │ ③ 读包文件
    ▼
  ③ 结构化访问 (只读消费者)
    │
    └── 开发者 / LLM Agent
```

**单向生产流水线：生成 → 保鲜维护 → 提供服务**。无循环依赖。

## 验证场景

### 场景：开发者修改 register.ts 的 @intent，CI 自动处理

**前提**：auth/ 文件夹包含 register.ts、validator.ts、user_repo.ts 等文件，已有 auth.yml 包且 pinned: false。

**触发**：开发者提交代码，register.ts 的 `@intent` 从 "注册请求处理" 改为 "注册请求接收与基础校验"。

1. **② 增量维护**：CI 检测到 register.ts 变更，重新计算 auth/ 的聚合 hash
   → 发现 `auth.yml` 中的 hash 不匹配
   → pinned: false，进入重算流程

2. **② 调用 ①**：收集 auth/ 的全部 `@intent` + 文件夹内依赖图
   → 传给 ① 聚类生成引擎

3. **① 聚类生成引擎**：LLM 识别语义簇，输出的 intent 和分组可能微调
   → 返回新结构化数据

4. **② 增量维护**：（假设调用成功）原子覆盖 `auth.yml`
   → CI 报告"auth 包已更新"

5. **③ 结构化访问**：另一位开发者使用 `get_intent_package("auth")`
   → 得到最新的意图包数据，注册组的 intent 已反映新的描述

### 异常分支：LLM 调用失败

在第 3 步，① 聚类失败返回错误 → ② 不覆盖 `auth.yml`，保留旧包，CI 报告警告 → ③ 读取时仍返回旧包，但无 stale 标记（因为 hash 不匹配的状态仅由 ② 掌握，③ 不主动做 hash 校验）。若需要 ③ 也能感知失效，可在读取时校验 hash，在返回中加 `stale: true`。

### 验证结论
- 三个核心功能全部参与：① 生成、② 检测+决策、③ 提供服务
- 关系矩阵中的依赖链（②→①、③→②）成立：② 需要 ① 的结果才能覆盖，③ 需要 ② 的数据才能返回
- "保留旧包"归入 ② 的异常处理分支，不新增功能

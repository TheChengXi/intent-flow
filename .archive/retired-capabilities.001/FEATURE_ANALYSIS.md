## 🔬 第一性原理分析

### 什么是编程的本质问题？

**核心矛盾**：
1. **认知负荷** vs **系统复杂度**
   - 人脑工作记忆：7±2 个信息单元
   - 现代软件：成千上万个文件和依赖关系
   
2. **变更速度** vs **理解成本**
   - 需求变化快：每周都要修改代码
   - 理解代码慢：需要追踪调用链、理解上下文

3. **知识传递** vs **团队流动**
   - 知识在老员工脑子里
   - 新员工加入/老员工离职 → 知识丢失

### 三个功能解决了什么本质问题？

| 功能 | 解决的本质问题 | 是否必要？ |
|------|---------------|-----------|
| **A. 依赖分析** | 降低认知负荷（快速建立心智模型） | ⚠️ 有替代方案 |
| **B. 架构检查** | 防止系统腐化（强制边界） | ✅ 必要 |
| **C. 骨架生成** | 降低变更成本（标准化起点） | ✅ 必要 |

### 功能 B：架构合规检查工具

#### 架构价值
```
价值：⭐⭐⭐⭐⭐ 防止架构腐化（自动化守护）
成本：⭐⭐ 一次性开发 + 规则配置
```

#### 为什么这个功能重要？

**真实场景**（架构腐化的典型路径）：
```
第 1 周：干净的三层架构
  Adapter → Application → Data

第 3 个月：出现快捷方式
  // 某个开发者为了赶工
  Controller 直接 import Database  ❌

第 6 个月：循环依赖
  ServiceA → ServiceB → ServiceC → ServiceA  ❌

第 1 年：无法重构
  依赖关系像意大利面，谁都不敢动
```

**架构检查工具的价值**：
```
✅ 在 PR 阶段就拦截违规代码
✅ 强制执行分层原则（自动化，不依赖人工 Review）
✅ 防止循环依赖（技术债务的主要来源）
```

#### 与 ESLint/ArchUnit 的对比

| 工具 | 覆盖范围 | 学习成本 | 集成难度 |
|------|---------|---------|---------|
| **ESLint** | 代码风格 | 低 | 易 |
| **ArchUnit** | 架构规则 | 高（需要 Java） | 难 |
| **你的工具** | 架构规则 | 低（配置式） | 易 |

**竞争优势**：
- ✅ 针对你的分层架构（Data/Application/Adapter）
- ✅ 理解 @intent 注释（语义级检查）
- ✅ 集成到现有工具链（MCP）

**结论**：
- ✅ **强烈推荐实现**
- ✅ 是三个功能中**唯一不可替代**的
- ✅ 长期 ROI 最高（防止技术债）

#### 架构师建议的规则

```yaml
rules:
  # 分层规则
  - name: "no_reverse_dependency"
    description: "数据层不能依赖应用层/适配层"
    check: "Data/** → !(Application|Adapter)/**"
  
  - name: "no_cross_adapter"
    description: "适配器之间不能互相依赖"
    check: "Adapter/MCP → !Adapter/VSCode"
  
  # 循环依赖
  - name: "no_circular_dependency"
    description: "禁止循环依赖"
    check: "A → B → C → !A"
  
  # 命名规范
  - name: "repository_in_data_layer"
    description: "Repository 必须在数据层"
    check: "*Repository.ts → Data/**"
```

## 🤖 AI 辅助编程视角

### AI 真正需要什么？

**误区**：AI 需要"能力清单"来理解代码
**现实**：AI 需要的是**快速定位上下文**

#### 功能 A：依赖分析

**AI 的真实工作流**：
```
用户："修复 MCPServer 的 bug"
  ↓
AI：Read("src/adapter/mcp/MCPServer.ts")  // 直接读
  ↓
AI：Grep("MCPServer", type: "ts")         // 查找引用
  ↓
AI：Read 相关文件 → 定位问题 → 修复
```

**你的工具加入后**：
```
用户："修复 MCPServer 的 bug"
  ↓
AI：generate_capability_list({ entryFiles: ["MCPServer.ts"] })
  ↓
AI：解析返回的 JSON → 提取依赖列表
  ↓
AI：Read 相关文件 → 定位问题 → 修复
```

**对比**：
- 你的工具：**多了一个中间步骤**
- 收益：提供了 @intent（语义信息）
- 成本：需要解析 JSON、绝对路径

**结论**：
- ⚠️ 对 AI 的价值有限（AI 更擅长直接读代码）
- ✅ 除非 @intent 的质量非常高

#### 功能 B：架构检查

**AI 的痛点**：
```
问题：AI 生成的代码可能违反架构规则

例子：
  用户："给 UserRepository 添加日志"
  AI 生成：
    import { Logger } from '../adapter/Logger'  ❌
    // 数据层不应该依赖适配层！
```

**你的工具加入后**：
```
AI 生成代码
  ↓
自动运行：check_architecture(changedFiles)
  ↓
发现违规：❌ Data layer cannot import from Adapter
  ↓
AI 自动修复：
  import { ILogger } from '../application/ILogger'  ✅
```

**结论**：
- ✅ **对 AI 非常有用**
- ✅ 类似 TypeScript 类型检查（即时反馈）
- ✅ 让 AI 生成的代码符合架构规范

#### 功能 C：骨架生成

**AI 的痛点**：
```
问题：AI 不知道你的项目约定

例子：
  用户："添加积分系统"
  AI：我该用 Service 还是 UseCase？
  AI：Repository 放在哪个目录？
  AI：依赖注入怎么写？
  → AI 需要反复询问或猜测
```

**你的工具加入后**：
```

  ↓

  ↓
AI：自动生成标准骨架
  ↓
AI：在骨架基础上填充业务逻辑
  → 无需询问约定，自动符合规范
```

**结论**：
- ✅ **对 AI 非常有用**
- ✅ 相当于"项目约定的可执行文档"
- ✅ 减少 AI 的猜测和试错

## 🆕 附录：reason 字段设计方案

### 问题背景

在依赖分析工具的设计中，讨论了是否需要添加 `reason` 字段来说明"为什么 A 文件依赖 B 文件"。

### @intent vs reason 的区别

| 字段 | 视角 | 回答的问题 | 示例 |
|------|------|-----------|------|
| **@intent** | 文件自己 | "我是谁？我为什么存在？" | "用户数据持久化的抽象边界" |
| **reason** | 调用者 | "调用者为什么需要我？" | "UserService 需要持久化用户数据" |

### 真实场景对比

```typescript
// UserService.ts 的依赖
dependencies: [
  {
    file: "UserRepository.ts",
    
    // @intent（文件自己的描述）
    intent: "用户数据持久化的抽象边界。应用层通过这个接口访问用户数据。",
    
    // reason（UserService 为什么要用它）
    reason: "UserService 需要持久化用户数据到数据库"
  }
]
```

### 关键洞察

**如果 @intent 写得好**（按照项目 GLOSSARY 的规范）：
- @intent 已经包含"它被谁使用，用来做什么"
- @intent 已经包含"它与其他模块的关系"
- reason 的增量价值有限

**reason 的真正价值场景**：
```typescript
// 同一个文件被不同调用者使用

// UserService.ts 的视角
Logger.ts
  intent: "统一日志记录服务"
  reason: "记录用户操作的审计日志"  ← UserService 特定用途

// PaymentService.ts 的视角  
Logger.ts
  intent: "统一日志记录服务"          ← 同一个 intent
  reason: "记录支付交易的合规日志"   ← 但 reason 不同！
```

### 实现方案

#### 方案 1：不添加 reason（推荐）
**理由**：
- ✅ 项目的 @intent 规范已经很完善
- ✅ 保持简单，降低维护成本
- ✅ 等实际使用中发现需求再加

**适用场景**：
- 单人开发
- 小团队
- @intent 质量高的项目

---

#### 方案 2：添加最简 reason（自动生成）
**实现**：
```typescript
{
  file: "UserRepository.ts",
  intent: "用户数据持久化的抽象边界",
  reason: "在第 42 行被调用"  // 自动分析调用位置
}
```

**优点**：
- ✅ 无需手动维护
- ✅ 提供基础的上下文信息

**缺点**：
- ⚠️ 信息价值有限（只是位置）

---

#### 方案 3：添加语义化 reason（混合模式）
**实现**：
```typescript
// 支持手动标注
import { Logger } from './Logger'; // @reason: 记录审计日志

// 或自动分析调用上下文
constructor(private logger: Logger) {}  // → reason: "构造函数依赖注入"
```

**优点**：
- ✅ 信息价值高
- ✅ 灵活：可手动可自动

**缺点**：
- ❌ 实现复杂
- ❌ 需要维护成本

---

### 最终建议

**优先级**：
- **P0（当前）**：不添加 reason，保持简单
- **P2（未来）**：如果实际使用中发现需要，再考虑方案 2 或 3

**判断标准**：
- 如果经常遇到"为什么这个文件依赖那个文件？"的困惑 → 添加 reason
- 如果 @intent 已经够用 → 不需要 reason

**实施建议**：
1. 先完善 @intent 的书写质量（按 GLOSSARY 规范）
2. 实际使用依赖分析工具 2-4 周
3. 根据实际痛点决定是否需要 reason
4. 如果需要，优先选择方案 2（自动生成，低成本）

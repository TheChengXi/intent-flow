# 后续想法：project-intent-hardening

## 未决 / 延后项

### 1. 提取器标签边界语义重构
- **现状**：`extractIntentFromLines` 遇 `@tag` 行停止解析，是 IntentFlow 注释体系的有意设计。本轮以投射侧转义（行首 `@` → `\@`）规避。
- **触发条件**：若未来出现跨块粘连需求（@intent 块内允许嵌套标签），需重新设计边界语义（如标签白名单集合），改动面涉及所有消费 `extractIntentFromLines` 的用例。
- **约束**：重构前必须先盘点消费方（当前已知 `ProjectIntentsToFilesUseCase` 两处调用）。

### 2. 转义规则表的可扩展性
- **现状**：规则硬编码在两个 replace 中，测试锁定。
- **触发条件**：若发现新的注释特殊序列（如行注释场景的 `//` 前缀、Rust 的 `/*!` 文档注释风格），将规则升级为可配置表结构，并补充对应测试。
- **注意**：Rust 目前按块注释 `/** */` 处理，若引入 `/*!` 内部文档风格需单独评估。

### 3. 投射后回读验证（可选增强）
- **现状**：工具只写不验。
- **触发条件**：若出现"转义规则漏网导致生成坏文件"的真实案例，可在 `ProjectIntentUseCase.execute` 写入后增加回读校验（词法解析），失败即抛错。
- **权衡**：增加一次读+解析开销；目前转义规则已被测试锁定，优先级低。

## 编译端定论（2025-08-01 讨论沉淀）

- **块注释“第一个终止序列（星号斜杠）即闭合”是语言词法规范**：C 语言 1972 年定下，所有语言继承；编译器/IDE 从左往右流式扫描 + 状态机，状态切换不可回退，不存在“从右往左/灵活判断”的选项
- **问题属于编译端，与工具层无关**：废弃 MCP 工具改用原生读写，内容含裸终止序列照样炸；工具保留且转义后即安全（转义是“保持块注释”前提下唯一自动方案）
- **业界先例全部转义**：Prisma #29736、Google FlatBuffers #8725（安全漏洞级）、GraphQL Codegen #2470、OpenAPI Generator #19528；StackOverflow 标准答案即星号反斜杠斜杠
- **风险只来自 ASCII 内容**（英文/代码片段/URL 中“星号紧贴斜杠”形态）；中文文本天然安全（无 ASCII 序列），故 @intent 表述用“星号斜杠”中文即可规避
- **手写代码不会触发**（正常人不写）；专砸代码生成器——本项目 @intent 投射本质是生成器（外部文本注入代码），故必然踩中

## 经验备忘

- **grep 残留检查假阳性**：`FileRepository` 模式会匹配到活接口 `IFileRepository`。复查残留请用精确路径模式：`from.*repositories/FileRepository'`。
- **投射含特殊字符文本前先转义**：本次 `*/` 坑在 IntentExtractor.ts 曾造成 TS1127/TS1109，已由工具侧转义根治。

## 执行期新发现（2025-07-31）

### intent-flow_project_intent 替换 @intent 时残留旧块碎片
- **现象**：force=true 替换已有 @intent 时，旧块尾部两行被重复残留；且新 @intent 被插入到旧块内部（旧块残头 + 新块 + 重复内容），导致文件 @intent 元数据污染（本次在 ProjectIntentUseCase.ts 手工清理两次）。
- **影响**：替换后的文件 @intent 含重复/截断行，破坏规格一致性；本次 feature 的转义只解决注释文本特殊字符，未覆盖此替换算法缺陷。
- **触发条件**：真实用户再次用该工具 force 更新 @intent 时即触发。
- **建议**：独立 feature 修复 replaceWithTreeSitter/replaceWithRegex 的替换范围边界（合并兄弟注释节点时可能吞掉旧块尾部，或插入点定位错误）；修复后需对既有 @intent 文件做一次全量重投射验证。

# 需求文档：codebase-health-check

## 项目意图
对 `src/` 全目录做一次综合健康检查（架构分层 + @intent 契约 + 代码质量），发现问题全部直接修复，最后输出一份综合诊断报告。

## 功能清单
1. **架构健康检查**：分层是否清晰、依赖方向是否合规、跨层/反向依赖检测
2. **@intent 契约检查**：覆盖率达 100%、描述质量、与代码行为一致性
3. **代码质量检查**：文件过大（>400 行）、死代码、未使用导出、命名一致性
4. **自动修复**：检查发现的问题全部直接修复，不做逐项确认
5. **诊断报告**：汇总问题清单、修复记录、剩余风险，落盘为报告文档

## 核心功能

### 核心功能1：架构健康检查
- **能力**：系统能够沿入口文件追踪依赖链，检测 src/ 下各层（data / application / adapter / types）之间的依赖关系，识别跨层依赖与反向依赖
- **业务价值**：暴露分层腐化风险，保证三层架构（data←application←adapter）方向可维护

### 核心功能2：@intent 契约检查
- **能力**：系统能够扫描 src/ 下全部源文件，检查 @intent 注释存在性（覆盖率目标 100%）、描述质量（非空、有实质内容）与代码行为的匹配度
- **业务价值**：@intent 是 IntentFlow 的核心契约，覆盖率缺失会直接导致后续 AI 协作与检索失效

### 核心功能3：代码质量检查
- **能力**：系统能够检查文件大小（>400 行标记为过大）、未使用的导出/死代码、命名一致性等常规质量项
- **业务价值**：保持代码库可读性与可维护性，防止文件膨胀与死代码累积

## 业务规则

### 依赖方向合规
- **场景**：检查 adapter / application / data 层之间及 types 共享层的 import 关系
- **行为**：仅允许上层依赖下层（adapter → application → data）；types 作为共享类型层可被任意层依赖；出现跨层跳过（如 adapter 直接依赖 data）或反向依赖（data 依赖 application）时记为架构问题
- **异常处理**：无法自动判定归属的文件（如入口文件、独立脚本）跳过判定并在报告中注明

### @intent 覆盖率
- **场景**：扫描 src/ 下所有 .ts 源文件
- **行为**：每个文件必须存在 @intent 注释，内容需描述该文件职责而非空占位；缺失或空白的文件直接补齐/重写 @intent
- **异常处理**：测试文件、配置文件等非业务源文件不强制要求，报告中单独归类

### 文件大小阈值
- **场景**：检查 src/ 下所有源文件行数
- **行为**：超过 400 行标记为"文件过大"，列入报告问题清单
- **异常处理**：过大文件不自动拆分为本次修复范围，仅报告并给出拆分建议（拆分属于结构性改动，需独立 feature）

### 修复策略
- **场景**：检查发现的所有可修复问题
- **行为**：全部直接修复，不做逐项确认；修复动作记录到报告中
- **异常处理**：涉及结构性重构（如文件拆分、接口重排）的问题只报告不修，列入延后

## 预设测试

### 前置条件
- 项目在 D:/w_dev/intent-flow，src/ 下含 adapter / application / data / types 四个目录
- 可使用 intent-flow MCP 工具（check_file_size、trace_dependency_chain、project_intent）

### 测试步骤

1. **依赖链检查**：对 src/ 入口文件执行依赖链追踪
   **预期结果**：输出按同层/跨层分组的依赖清单，跨层依赖可明确判定合规与否

2. **@intent 全覆盖扫描**：遍历 src/ 下全部 .ts 文件检查 @intent
   **预期结果**：非业务源文件外 100% 覆盖；缺失文件已补齐

3. **文件大小扫描**：对全部源文件执行大小检查
   **预期结果**：>400 行文件全部列出，报告中含拆分建议

4. **报告产出**：检查与修复完成后输出综合报告
   **预期结果**：报告含问题清单、修复记录、剩余风险三部分

### 异常场景

- **文件归属不明**：无法判定层的文件 → 跳过判定，报告中注明原因
- **修复引入新问题**：补齐 @intent 后文件出现语法问题 → 回滚该文件修复并记录
- **覆盖目标达不到 100%**：存在无法安全补齐 @intent 的文件 → 报告中标记为已知残留并说明原因

## 边界收束

**此时必做**：
- 架构依赖方向检查（决定分层是否健康）
- @intent 覆盖率检查与补齐（契约是框架核心）
- 文件大小与死代码检查（常规质量基线）
- 综合报告输出（本次体检的交付物）

**此时不做**：
- 过大文件自动拆分 — 结构性重构风险高，需独立 feature 先做设计
- 依赖漏洞/CVE 审计 — 需联网查询漏洞库，属安全范畴，与本体检目标不同
- 运行期行为验证 — 超出静态体检范围，如需要可另起测试 feature

## 实现取向

协作者开始设计实现前需要知道的技术取向声明。属于需求澄清，不是结构设计，也不是技术栈选型或具体代码实现。

- **工具复用**：优先使用项目现有 intent-flow MCP 工具（`trace_dependency_chain` 查依赖、`check_file_size` 查大小、`project_intent` 补 @intent），不足处用静态分析（grep/find/ts 类型检查）补充
- **修复前置**：任何修复动作前先读文件确认上下文，避免盲改；补齐 @intent 遵循项目既有注释风格
- **报告结构**：问题清单（按严重度排序）→ 修复记录（改了什么）→ 剩余风险（未修项及理由），三部分固定结构
- **零新增依赖**：本次体检不引入新的 npm 依赖，全部用现有工具与脚本完成

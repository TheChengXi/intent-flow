# later-on：guard-toggle 后续想法备忘

> 记录本次设计明确不做、但值得后续评估的事项。按触发条件排序。

## 1. 分规则开关
- **想法**：独立控制 edit/write 确认 与 bash 危险命令确认
- **触发条件**：出现"只想放行 edit 保留 bash 保护"的真实诉求
- **影响面**：`IGuardToggleService` 接口需扩展为按规则查询；配置文件结构从 `{enabled}` 变为规则级；命令需带参数

## 2. 切换时安全确认弹窗
- **想法**：关闭守卫（尤其关闭 bash 审查）时弹一次确认，防止误关
- **触发条件**：误关事故频发，或用户明确要求
- **影响面**：`GuardToggleCommand` handler 内加 `ctx.ui.confirm`

## 3. TUI 常驻状态组件
- **想法**：TUI 界面常驻显示当前模式（审查中 / 放行中），避免"记不住当前状态"
- **触发条件**：用户反馈切换后无法感知当前模式
- **影响面**：新增 tui 组件，参考 `SubAgentView` 先例；需订阅 service 状态变更

## 4. 跨项目共享开关（用户主目录级）
- **想法**：`~/.intentflow-guard.json` 全局生效，多项目统一审查策略
- **触发条件**：出现多项目统一管理诉求
- **影响面**：`GuardToggleStore` 路径策略化；需定义项目级与全局级的优先级

## 5. CLI flag 启动时指定
- **想法**：`--guard-off` 启动即放行（配合 pi 的 `registerFlag`）
- **触发条件**：出现"启动即放行"的批处理/脚本场景
- **影响面**：`extension.ts` 读 flag 初始化 service 初始状态

## 6. 配置文件写原子性
- **想法**：先写临时文件再 rename，防止写一半崩溃产生损坏文件
- **触发条件**：观察到损坏文件实际发生（当前读取端已有安全态回退兜底，损坏仅影响"切换前"的短暂窗口）
- **影响面**：`GuardToggleStore.write()` 内部实现

## 7. 多进程并发修改配置文件
- **想法**：多个 pi 实例（或子进程）同时 toggle 时状态互相覆盖
- **触发条件**：确认存在多实例同项目并发使用场景
- **影响面**：store 加文件锁或最后写入者胜出策略

## 8. 子 agent 与主 agent 状态一致性
- **想法**：子 agent 进程读不到主进程内存开关状态（子 agent 本就经 PI_EXT_SKIP 放行，当前无行为差异）
- **触发条件**：开关语义未来变为"仅主会话放行"或子 agent 改为默认拦截时
- **影响面**：子进程环境注入开关状态（参考 `SCOPE_SKIP_ENV` 注入先例）

## 9. 闲置文件清理
- **想法**：`src/data/services/scope/IAccessPolicy.ts` 自述"疑似闲置，待清理确认"
- **触发条件**：清理类 feature（如 `unused-code-cleanup`）或维护窗口
- **影响面**：删除文件 + 确认无引用（当前无 import 引用）

## 10. 测试覆盖补强
- **想法**：集成测试覆盖 `/guard-auto` 命令全流程（含持久化断言）
- **触发条件**：实现阶段单测通过后，若有命令层测试先例可仿照
- **影响面**：`GuardToggleCommand` 的测试文件
